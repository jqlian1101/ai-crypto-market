# 行情脚本用法说明

本文档说明 `scripts/` 下两个行情脚本的用法：补数脚本 `backfill_market.py` 与校验脚本 `verify_market_candles.py`。

以下命令均在仓库根目录执行，使用项目虚拟环境 `.venv`。

---

## 一、前置条件

1. 启动 PostgreSQL 与 Redis：

   ```powershell
   docker compose up -d
   ```

2. `.env.local` 中配置 `DATABASE_URL`（数据库用户为 `aicrypto`）与 `REDIS_URL`。
3. 数据库迁移到最新版本：

   ```powershell
   .\.venv\Scripts\python.exe -m alembic -c migrations\alembic.ini upgrade head
   ```

4. 运行机器能访问 `api.binance.com` 与 `fapi.binance.com`。两个脚本都使用 Binance 公共接口，无需 API Key。

---

## 二、补数脚本 `scripts/backfill_market.py`

从 Binance 公共 REST 接口分页拉取已收盘 K 线，幂等写入 `market_candles`，`source` 固定为 `REST_BACKFILL`。

### 用法

```powershell
# 演练：只拉取与校验，不写库
.\.venv\Scripts\python.exe scripts\backfill_market.py --days 7 --dry-run

# 正式写入最近 7 天
.\.venv\Scripts\python.exe scripts\backfill_market.py --days 7

# 只补指定标的、市场与周期
.\.venv\Scripts\python.exe scripts\backfill_market.py --symbols BTCUSDT --market-types SPOT --timeframes 1h --days 3
```

### 参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--symbols` | `MARKET_SYMBOLS` 配置项 | 逗号分隔，如 `BTCUSDT,ETHUSDT` |
| `--market-types` | `MARKET_TYPES` 配置项 | 可选 `SPOT`、`USDM_FUTURES` |
| `--timeframes` | `MARKET_TIMEFRAMES` 配置项 | 可选 `1m`、`5m`、`15m`、`1h`、`4h` |
| `--days` | `7` | 从当前时间向前补的天数，必须大于等于 1 |
| `--dry-run` | 关闭 | 只拉取与校验，不写库 |

### 行为说明

- 只写已收盘 K 线。未收盘的最后一根会被排除。
- 重复执行安全。主键冲突时以 REST 数据覆盖已有行。
- 单组（市场 × 标的 × 周期）失败不会中断其余组。失败项会记录日志并计入失败数。
- 写入前校验 OHLC 与非负量。非法行会被拒绝并计入失败数。
- 请求之间固定间隔 0.25 秒，避免触发限速。
- 偶发的 SSL 或网络错误可直接重跑，结果是幂等的。

### 退出码

- `0`：全部成功。
- `1`：存在失败组，或参数非法。

## 三、校验脚本 `scripts/verify_market_candles.py`

只读检查 `market_candles` 数据质量，可重复执行，不会修改数据。

### 用法

```powershell
# 仅查数据库，约 1 秒
.\.venv\Scripts\python.exe scripts\verify_market_candles.py

# 额外抽样每组最新 N 根，与 Binance 逐字段比对
.\.venv\Scripts\python.exe scripts\verify_market_candles.py --sample 3
```

### 参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--sample N` | `0`，不比对 | 每组抽样最新 N 根，与 Binance 的 OHLCV、成交笔数逐字段比对 |

### 检查项

1. 重复 `open_time`。
2. 未收盘 K 线（`close_time > now`）。
3. OHLC 与非负量非法行。
4. 来源不是 `REST_BACKFILL` 的行。
5. 相邻 `open_time` 之间的缺口。
6. 抽样与 Binance 不一致（仅 `--sample` 时执行）。

每组输出一行结果。有问题的组以 ERROR 级别输出具体项。

### 退出码

- `0`：全部通过。
- `1`：存在失败项。

可用于定时任务或 CI。

## 四、同步模型单价 `scripts/sync_model_pricing.py`

把 `config/base.toml` 的 `[llm.model_pricing]` 段同步进 `model_pricing` 表。
**没有这一步，LLM 调用的费用只能记 0**（单价缺失会被显式标记
`price_snapshot.priced = false`，绝不静默当成「免费」）。

### 用法

```powershell
# 首次同步（或版本未变时重复执行，幂等）
.\.venv\Scripts\python.exe scripts\sync_model_pricing.py

# 供应商调价后：改 base.toml 的单价，并递增版本号
.\.venv\Scripts\python.exe scripts\sync_model_pricing.py --pricing-version v2
```

### 参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--pricing-version` | `v1` | 单价版本号。**调价时必须递增** |

### 版本纪律

`model_pricing` 的主键是 `(model_id, pricing_version)`。

- 同版本号下单价内容变了 → 脚本**直接报错**，不原地覆盖。
  原地覆盖会让历史 `llm_cost_records.pricing_version` 指向新价格，
  审计时无法回答「这条成本当时按哪个价算的」。
- 递增版本号 → 新增一行，旧行保留。
  `resolve_pricing()` 按 `effective_from` 取当时生效的最新一条。

### 输出

```
单价同步完成：新增 3，跳过 0，更新 0
```

## 五、成本报表 `scripts/report_llm_costs.py`

只读汇总 `llm_cost_records`，回答三个问题：
「这个月花了多少」「哪个 Agent 最贵」「哪版 Prompt 最烧 token」。

### 为什么需要它

成本数据早就落库了，但**长期没有任何东西读它**——
又一个「有表无读方」。没有报表就没有基线，
而「多 Agent 拆分是否值得」这个问题**只能靠成本报表回答**：
拆分会让调用量成倍上升，没有成本数据就无法判断收益。

### 用法

```powershell
# 最近 30 天（默认）
.\.venv\Scripts\python.exe scripts\report_llm_costs.py

# 最近 7 天
.\.venv\Scripts\python.exe scripts\report_llm_costs.py --days 7

# 指定区间（UTC）
.\.venv\Scripts\python.exe scripts\report_llm_costs.py --since 2026-11-01 --until 2026-12-01

# JSON 输出（便于接入其他工具）
.\.venv\Scripts\python.exe scripts\report_llm_costs.py --json
```

### 参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--days N` | `30` | 回看天数；与 `--since` / `--until` 互斥 |
| `--since` | 无 | 起始时间（UTC），如 `2026-11-01` |
| `--until` | 无 | 结束时间（UTC），如 `2026-12-01` |
| `--json` | 关闭 | 输出 JSON 而非文本表格 |

### 输出分组维度

模型 / Agent / 档位 / Prompt 版本 / 调用状态 / 按日。

`prompt_version` 与 `status` 从 `model_runs` **LEFT JOIN** 取
（`llm_cost_records` 没有这两列）。

### 读数纪律：未定价 ≠ 免费

`llm_cost_records.estimated_cost_usd` 是 **NOT NULL**，
单价缺失时只能写 0。因此：

- 费用**只**累加 `price_snapshot.priced == true` 的行；
- 未定价行**单独计数**，其 token 仍计入总量（那是真实消耗）；
- 报表会明确提示「费用是**下界**，不是实际支出」，
  并列出哪些模型没有价格。

**处置方式**：给这些模型补 `model_pricing` 行
（本地模型登记 0 价即可）。**先跑 `scripts/sync_model_pricing.py`**
——单价没同步时，所有调用的费用都是「未知」而不是「零」。

> 与 L-05「键缺失 ≠ 费率为 0」同源。
> 报表若直接把 0 汇总会让成本**系统性低估**，而且**看不出低估**。

### 退出码

- `0`：正常（含「存在未定价调用」的情况——那是数据事实，不是脚本故障）。
- `1`：参数非法或取数失败。

## 五之二、多 Agent 分析路径（无独立脚本）

多 Agent 拆分（PRD 4.7 / 24.4）**没有单独的 CLI**——
它通过分析工作进程触发，与单 Agent 路径共用同一套脚本。

### 两条路径

| 路径 | 入口 | 调用次数 | 用途 |
|---|---|---|---|
| 单 Agent（对照） | `analysis_worker.process_one` | 1 | PRD 4.7.3 的**对照组**，不能删 |
| 多 Agent | `analysis_worker.process_one_multi` | 7（6 子 + 1 Master） | 正式路径 |

**单 Agent 路径必须保留**——PRD 4.7.3 要求做
「规则基线、单模型综合分析和多 Agent 分析」的**配对比较**，
单 Agent 正是对照组。

### 怎么跑多 Agent 路径

目前**需要显式调用** `process_one_multi`（尚未接入调度层，
P5 会把它做成定时任务）。最小调用方式：

```python
from aicrypto.config.settings import get_settings
from aicrypto.services.analysis_worker import process_one_multi

process_one_multi(get_settings())
```

### 成本影响（务必先看）

多 Agent 的调用量是单 Agent 的 **7 倍**。
跑之前建议**先出一份基线报表**：

```powershell
# 拆分前基线（只跑过单 Agent 时的费用）
.\.venv\Scripts\python.exe scripts\report_llm_costs.py --days 30
```

多 Agent 跑过之后，报表的「按 Agent 分组」会显示
`technical` / `structure` / `derivatives` / `liquidity` / `regime` /
`risk` / `master` 七行——
**这正是 L-33 修掉的那个缺陷所解锁的能力**：
此前所有调用的 `agent_name` 都记成 `"master"`，
「哪个 Agent 最贵」永远答不出来。

### 排查用表

多 Agent 跑完后，`agent_runs` 会有 7 行、`agent_outputs` 有 6–7 行
（失败的 Agent **只有** `agent_runs`、**没有** `agent_outputs`——
这是 PRD 32.4 的红线：绝不伪造输出）。

```sql
-- 每个 Agent 的状态
SELECT agent_name, status, tier, duration_ms, prompt_version
FROM agent_runs
ORDER BY started_at DESC;

-- 失败/降级的 Agent（这些**不会**出现在 agent_outputs 里）
SELECT agent_name, status, degraded_reason, error
FROM agent_runs
WHERE status <> 'SUCCESS';

-- 每次 Agent 调用消耗的 token 与费用（靠 agent_run_id 关联）
SELECT ar.agent_name, mr.input_tokens, mr.output_tokens,
       lc.estimated_cost_usd, lc.price_snapshot->>'priced' AS priced
FROM agent_runs ar
JOIN model_runs mr ON mr.agent_run_id = ar.run_id
JOIN llm_cost_records lc ON lc.model_run_id = mr.model_run_id
ORDER BY mr.created_at DESC;
```

> 最后那条 JOIN **在 L-33 修复前查不出任何东西**
> （`model_runs.agent_run_id` 恒为 NULL）。

## 六、校验脚本 `scripts/verify_partial_result_timeout.py`

验证 PRD 24.4「超时时输出『分析超时 + 已完成部分』」的**真实端到端行为**。

### 为什么需要它

MockTransport 在进程内直接返回响应，**根本没有真实 socket**，
所以它验不出「连接建立后服务端真的不回应」这种超时——
而这正是生产上最常见的超时形态（网关挂起、连接池半死、上游推理卡住：
**请求发出去了，钱也花了，就是没有响应**）。

这个脚本起一个**真实的 HTTP 服务器**（真 socket、真 accept），
客户端连上去后服务器**读完请求就故意不回应**，
直到客户端超时断开——触发货真价实的 `httpx.ReadTimeout`。

### 用法

```powershell
# 需要本地 Postgres 可连（脚本会造数据并在结束时清理）
.\.venv\Scripts\python.exe scripts\verify_partial_result_timeout.py
```

### 验证内容

| 项 | 期望 |
|---|---|
| `analysis_runs.status` | `PARTIAL` |
| `analysis_reports.status` | `PARTIAL` |
| `analysis_reports.degraded` | `True` |
| `analysis_reports.degraded_reason` | `TIMEOUT`（**不是** `MODEL_CALL_FAILED`） |
| `content.market_bias` | `UNAVAILABLE`（**不是** `NEUTRAL`） |
| `content.scenarios` / `scenario_probabilities` / `dominant_factors` | 全空（**不伪造结论**） |
| `content.evidence` | 非空，且 `source_path` 指向快照里的真实字段 |
| `model_runs` | 非空（**失败的尝试也必须记账**，L-24） |

脚本会在结束时**清理自己造的数据**，可重复执行。

## 七、推荐流程

```powershell
.\.venv\Scripts\python.exe scripts\backfill_market.py --days 7
.\.venv\Scripts\python.exe scripts\verify_market_candles.py --sample 3
```

先补数，再校验。两步都返回 `0` 即为通过。

看 LLM 成本时：

```powershell
# 先确保单价已同步（否则所有费用都是「未知」）
.\.venv\Scripts\python.exe scripts\sync_model_pricing.py

# 再出报表
.\.venv\Scripts\python.exe scripts\report_llm_costs.py --days 30
```

**顺序不能反**：单价没同步时报表显示的费用是**下界**，
不是实际支出——这正是报表会显式警告的情形。

## 八、已知注意事项

- SPOT BTCUSDT 4h 比其他组多 13 根，最早为 `2026-11-10 20:00 UTC`。这些数据来自本次补数窗口之前的运行，校验判定为合法，但来源无法确认。是否保留需要人工决定。
- 尚未为补数与校验两个脚本编写 `tests/` 自动化测试。
- 两个脚本各自定义了 `ENDPOINTS` 与 `TIMEFRAME_MS`，修改时需同步。
- `sync_model_pricing.py` 的同步逻辑有集成测试覆盖
  （`tests/integration/test_model_pricing_sync.py`）。
- `verify_partial_result_timeout.py` 会**真实地发 HTTP 请求**到本机临时端口
  并**造/删数据库数据**，请勿在生产库上执行。
- `report_llm_costs.py` 是**只读**脚本，可随时在生产库上跑。
  但若提示「存在未定价调用」，其费用数字是**下界**——
  先跑 `sync_model_pricing.py` 补单价，再解读费用。
  成本报表逻辑有单元测试与真库测试覆盖
  （`tests/unit/test_cost_report.py` / `tests/integration/test_cost_report.py`）。
