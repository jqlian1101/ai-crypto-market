## 0. 摘要（先给结论）

| 成本项 | 结论 | 量级 |
|---|---|---|
| **市场行情数据** | **完全免费**。Binance 现货 + USDⓈ-M 期货的 REST / WebSocket 公共接口不收费、不需要账号权限 | $0 |
| 通知渠道（飞书 / 企业微信） | 免费，仅有平台频率限制 | $0 |
| 开源软件（Freqtrade / LangGraph / Next.js 等） | 免费 | $0 |
| **LLM API** | **唯一的主要变动成本**，且**完全由调用频率决定** | **$13 – $2,000 / 月**（跨度 150 倍） |
| 本地模型 | 电费 + 硬件折旧，可替代 60–90% 的 LLM API 支出 | ¥65 – ¥400 / 月（取决于已有硬件） |
| 存储 | 本地磁盘，10–20 GB/年 | $0（一次性硬件） |
| 基础设施 | 本地部署 = $0；若上 VPS = $5–10 / 月 | $0 |
| **参考：模拟交易成本假设** | 永续 taker 0.05%/边 → 一次往返 0.10% 名义 + Funding | 用于轨道 B 测算，非真实支出 |

**核心判断**：本项目的经济性风险**不在数据，而在 LLM 调用频率**。第 24 章的三档模型分层与「事件驱动优先」不是优化项，而是**成本闸门**——把 `analysis_1h` 从 24 次/天降到 8 次/天，月度 LLM 支出直接减少 40% 以上。

**建议预算**：

- 起步（3 个月内）：**$20 / 月**（全 Haiku 档 + 本地模型承担 15m 结构分析）
- 稳定期：**$60 – $120 / 月**（Light 用小模型，Standard 用 Sonnet 档，Deep 用 Opus/旗舰档，每日硬上限 $3）
- 保守上限（任意配置不得突破）：**$150 / 月**，超出按 24.2 的降级顺序执行

### 1.4 派生数据（Python 计算，不外购）

| 类别 | 内容 | 产出表 |
|---|---|---|
| 技术指标 | EMA 20/50/200、RSI、MACD、ADX、ATR、布林、成交量均值、VWAP | `market_metrics` |
| 市场结构 | Swing High/Low、支撑阻力区、趋势结构 HH/HL、突破回踩 | `market_structure_features`、`sr_zones` |
| 市场状态 | `UPTREND`/`DOWNTREND`/`RANGE`/`HIGH_VOL`/`LOW_VOL`/`BREAKOUT_ATTEMPT`/`TREND_REVERSAL`/`UNCERTAIN` | `market_regimes` |
| 快照 | 多周期摘要 + 指标 + 结构 + 衍生品 + 流动性 + 质量标记 + 版本号 | `market_snapshots`、`snapshot_data_refs` |
| 历史相似情景 | 结构化匹配结果（向量 / 特征距离） | `historical_pattern_matches` |
| 信号与预测 | Bias / Opportunity / Setup / Executable + 生命周期事件 | `signals`、`signal_events`、`prediction_observations` |
| 评估结果 | 方向准确率、Brier、区间覆盖、MFE/MAE、双轨经济性 | `prediction_evaluations`、`evaluation_results` |

**这些是本项目真正的"数据资产"**：原始行情可随时从 Binance 重拉（免费），但 `agent_outputs` + `snapshot` + `prediction_evaluations` 是**不可再生的**——它们依赖当时的模型版本、Prompt 版本与快照，任何一次丢失都会造成评估样本断层。因此**备份优先级：agent_outputs / market_snapshots / signals > 行情原始数据**（行情丢了可以重拉，评估丢了就断了）。

## 2. 数据来源清单与获取方式

### 2.1 主数据源：Binance（免费）

| 通道 | 端点 | 凭据 | 计费 | 限流 |
|---|---|---|---|---|
| Spot REST | `api.binance.com` | 公开接口**无需** API Key | **免费** | 按 IP 权重，6000 weight/min |
| Spot WS | `stream.binance.com:9443` | 公开 | **免费** | 每连接 ≤1024 stream，24h 强制断开 |
| Futures REST | `fapi.binance.com` | 公开接口无需 Key（私有接口需） | **免费** | 2400 weight/min |
| Futures WS | `fstream.binance.com` | 公开 | **免费** | 同上 |
| 服务器时间 | `/api/v3/time` | 公开 | 免费 | — |

**结论：行情数据 0 成本。** 无需申请账号、无需实名、无额度申请。这是本项目最大的成本优势——同类行情数据在商业 API（如 Kaiko、Coin Metrics、Amberdata）上按月订阅计费，行情单价通常 $100–$2,000/月。个人自用项目**完全没有必要**付这个钱。

### 2.2 调用量与限流余量测算

| 调用 | 频率 | 日请求数 | 权重（估） | 日权重 |
|---|---|---|---|---|
| OI 轮询 | 60s × 2 合约 | 2,880 | 1 | ~2.9k |
| Funding 历史 | 每 8h | 6 | 0 | ~0 |
| WS/REST 交叉核对（29.4.2） | 每 5 分钟 × 20 条流 | 5,760 | 2 | ~11.5k |
| Ticker / markPrice 兜底轮询 | 每 30s | 5,760 | 1 | ~5.8k |
| exchangeInfo | 每日 | 2 | 20 | ~0 |
| 历史补数（一次性 / 缺口修复） | 事件驱动 | 分页，≤1000 根/页 | 递增 | 突发，需 `RateLimiter` 统一退避 |

**WebSocket 连接数**：Binance 组合流单连接可承载 1024 个 stream，因此 Spot 1 条 + Futures 1 条连接即可覆盖全部 5 个周期 × 2 资产 + ticker + depth + aggTrade + markPrice。**不需要为每条流单独建连接**（这是常见的新手性能陷阱）。

**限流余量**：日权重约 20k，而限额是 6000 weight/**分钟**（≈ 8.6M/天）。**余量超过 400 倍**。唯一需要小心的是历史补数：1000 根/页时权重可达 10/页，单次全量补 2 币种 × 2 市场 × 5 周期 × 1000 根 ≈ 40 页，瞬间消耗数百权重。必须遵守 27.2 的「分页 + 退避 + 不并发重试」。

### 2.3 第二数据源（可选，交叉校验）

| 选项 | 获取方式 | 费用 | 建议 |
|---|---|---|---|
| Bybit v5 | 公开 REST/WS | 免费 | ✅ 推荐，若所在地区可访问 |
| OKX v5 | 公开 REST/WS | 免费 | ✅ 备选 |
| Coinbase | 公开 REST | 免费 | 现货对比可用 |
| 不引入 | Binance 自身多接口一致性 | 免费 | ✅ **最小可接受方案**（29.4.2 已承担该职责） |

**成本**：免费。**实际成本是维护成本**：多一套 Normalizer、一套字段映射、一套时钟对齐逻辑。

**建议**：**首期不引入**。PRD 29.4.2 的 WS↔REST 交叉核对已经覆盖了「单接口错误」，而「单交易所整体故障」在个人使用场景下概率极低（真发生了，你也不会想在那 5 分钟里做什么决定）。等主链路稳定后再加 Bybit，作为 27.1 的低频校验源（每 5 分钟拉一次最新价 + 5m K 线即可）。

**注意地域可用性**：Binance、Bybit、OKX 对部分地区有地域限制。如果部署环境无法访问 Binance，主数据源需要换（这是比费用更重要的选型约束，建议在 Phase 0 就用 `curl` 验证可达性）。

## 3. 数据源之外的"隐性数据成本"

这些不在"数据费"里，但会真实消耗预算：

| 项 | 说明 | 应对 |
|---|---|---|
| **快照膨胀** | 快照是 LLM 的唯一输入，字段越多 token 越多。PRD 4.8 的建议清单有 12 项，直接照做会让单次输入 token 轻易到 24k 上限 | 快照按 Agent 视图裁剪（24.4「各自独立快照视图」），不是所有 Agent 都看到全量 |
| **重复投喂同一份证据** | Master 汇总时若把 6 个子 Agent 的完整输出原样拼接，输入 token 翻倍 | Master 只收结构化摘要 + 引用 ID，需要细节时用 Reflection 定向追问（24.4） |
| **Prompt 缓存失效** | 快照内容每次都变 → 缓存前缀失效 → 无法享受 $0.10/M 的缓存价 | Prompt 缓存应作用于**固定的 system prompt + 固定工具定义**，快照放最后 |
| **历史回填的数据量** | 补 2 年 1m 数据 ≈ 2 币种 × 2 市场 × 1,050,240 根 ≈ 420 万行 | 按需回填：1m 只补近 90 天，5m+ 补满 2 年 |
| **重算成本** | 特征、指标、快照全量重算 | 快照按需生成 + 版本化缓存（13.3「计算结果可缓存并标明版本」） |

## 4. 成本测算

### 4.1 LLM API 成本（主要变动成本）

#### 4.1.1 单价基线（2026-11 公开价，USD / 1M tokens）

| 档位 | 代表模型 | 输入 | 输出 | 缓存输入 |
|---|---|---:|---:|---:|
| LIGHT | Claude Haiku 5.5 / GPT-6 Luna | 0.10 | 0.50 | 0.01–0.01 |
| LIGHT-2 | Gemini 3.1 Flash-Lite | 0.25 | 1.50 | 0.025 |
| STANDARD | Claude Sonnet 5.5 / GPT-6.1 Sol | 2.00 | 10.00 | 0.10 |
| STANDARD-2 | GPT-6.1 Terra / Gemini 4 Argon | 1.00–2.00 | 5.00–10.00 | 0.05–0.10 |
| DEEP | Claude Opus 5.5 | 4.00 | 20.00 | 0.20 |
| DEEP-2 | Claude Fable 5.1 / GPT-6 Astra | 10.00 | 50.00 | 0.25–1.00 |

> **价格会变**。Gemini 4 Argon 促销价 $2/$10 仅到 2026-11-30，之后 $4/$20（翻倍）；Gemini 3.8 Flash $0.75/$3.75 到 2026-12-31，之后 $1.50/$7.50（翻倍）。**测算必须按当期实时价格复算，不能硬编码在代码里**——建议把模型单价存进 `config_versions` 表或独立的 `model_pricing` 配置，由 Gateway 读取并随 `llm_cost_records` 记录「本次估算所用的单价版本」。

#### 4.1.2 调用量模型

按 PRD 23.1.2 任务清单 + 24.4 编排拓扑推算（**2 资产：BTC、ETH**）：

| 任务 | 次数/天/资产 | Agent 构成 | 输入 token/次 | 输出 token/次 |
|---|---:|---|---:|---:|
| `analysis_15m` | 96 | 2 × LIGHT（Structure, Technical），无 Master | 7,000 | 1,800 |
| `analysis_1h` | 24 | 6 × LIGHT（子 Agent）+ 1 × STANDARD（Master） | 33,000 | 7,900 |
| `analysis_4h` | 6 | 2 × LIGHT + 1 × STANDARD + 1 × STANDARD（Master） | 27,000 | 6,300 |
| 异动触发分析 | 17.5（估） | 1 × LIGHT + 1 × STANDARD 级 | 25,000 | 6,000 |
| `analysis_daily` | 1（全资产共享） | 1 × DEEP + 评估摘要 | 40,000 | 8,000 |
| `analysis_weekly` | 0.14（共享） | 1 × DEEP | 60,000 | 12,000 |

> 异动触发次数 17.5 次/天/资产是**假设值**（约 3.5 CRITICAL + 10 WARN），必须用 `anomaly_evaluations` 实测替换。**这是全模型中最大的不确定项**：阈值未校准时，误报可能把异动触发分析拉高 3–5 倍，直接把成本推到 DEEP 档水平。**先做 PRD 28.2 第 4/5 项（阈值校准 + 有效率基线），再定预算。**

|---|---:|---:|

#### 4.1.3 三种配置方案与月成本

| 方案 | 模型映射 | 天成本 | **月成本（30 天）** | 适合 |
|---|---|---:|---:|---|
| **A. 极限省** | 全部 LIGHT（Haiku $0.10/$0.50） | $0.42 | **$13** | 验证期、只跑确定性结论 |
| **B. 均衡（推荐）** | LIGHT→Haiku，STANDARD→Sonnet 5.5，DEEP→Opus 5.5 | ≈ $5.9 | **$177** → 优化后 **$60–120** | 稳定期个人自用 |
| **C. 全旗舰** | 全部→Fable 5.1 / Astra（$10/$50） | ≈ $67 | **$2,024** | 不推荐，无收益支撑 |

**方案 B 的优化后区间（$60–120/月）从哪来**：

| 优化项 | 节省 | 依据 |
|---|---:|---|
| Prompt 缓存命中 50%+ | 输入成本 ×0.7 | 固定 system prompt 前缀；快照置后 |
| `analysis_15m` 降到 4 次/天（15m→1h 聚合） | -$3 | PRD 23.2.2 本就只聚合不推送 |
| 异动触发次数实测后修正到 8/天 | -$2 | 依赖阈值校准 |
| 日报改用 Batch API（~50% off） | -$0.4 | 延迟容忍度高 |
| 合理缩减快照字段（4.8 的 12 项 → 按需 6–8 项） | -$1.5 | 输入 token 直降 |

> **方案 B 是现实的、方案 C 是浪费的**：把 TIER_LIGHT 的 6 个子 Agent 全部换成旗舰模型，月支出增加 $1,800+（折合 ¥13,000/月），而 PRD 24.1 已明确指出这些 Agent 的职责是「偏确定性」「可由规则直接得出的结论不调用 LLM」。**旗舰模型不会让结构摘要变得更准确，只会让账单更好看。**

#### 4.1.4 成本控制闸门（必须实现）

PRD 24.2 已给出降级顺序，建议补齐**具体的判定与动作**：

| 闸门 | 阈值 | 动作 |
|---|---|---|
| 单次分析输入上限 | 24k token | 超过 → 裁剪快照字段，标注 `snapshot_truncated=true` |
| 单 Agent 上限 | 8k token | 超过 → 拒绝并记 `llm_cost_records` |
| 单日全局 token | 按方案 B 反推 ≈ 4.5 M | 达到 80% → 停 TIER_DEEP |
| 单日费用硬上限 | **$3**（≈ $90/月） | 达到 → 降级顺序：停 DEEP → STANDARD 降 LIGHT → 关非关键 Agent → 仅推确定性结论 |
| 降级可见性 | 必须写 `degraded: true` + `degraded_reason` | 避免把便宜模型的结论与完整结论混在一起统计 |

**估算单价版本必须入库**：GPT-6 Astra 输入超 272K 时变为 $20/$75，Gemini 促销价会到期——Gateway 应记录「估算所用单价 + 单价来源日期」，否则成本报表会因为价格变动而失真。

### 4.2 本地模型成本

| 方案 | 一次性 | 月度 | 适用 |
|---|---:|---:|---|
| 已有本地 GPU（RTX 3090/4090） | $0 | **电费 ≈ ¥65 / 月** | 最佳性价比 |
| 新购 4090/5090 | ≈ ¥14,000–20,000 | 折旧（3 年）≈ ¥400–550 / 月 + 电费 | 长期重度使用才划算 |
| 云 GPU 租用 | — | $0.35–0.60 / 小时 × 8h/天 × 30 ≈ **$84–144 / 月** | 无硬件时的替代 |
| 纯 CPU（Ollama，14B Q4） | $0 | 电费 ≈ ¥25 / 月，但**速度不足** | 仅 7B 以下小模型可用 |

**GPU 时间估算**（本地 14B Q4，RTX 4090，prefill ≈ 2,000 tok/s，decode ≈ 60 tok/s）：

```
日 token 量 4.18M 输入 + 0.82M 输出
prefill: 4.18M / 2,000  ≈ 2,090 s  ≈ 0.58 h
decode : 0.82M / 60     ≈ 8,500 s  ≈ 2.36 h
合计 ≈ 3 h/天 → 90 h/月
功耗 ≈ 400 W → 0.4 kW × 3 h = 1.2 kWh/天 → 36 kWh/月
电费（¥0.6/kWh）≈ ¥22/月
```

**结论**：本地模型约 3 h/天 GPU 占用即可覆盖全量 LIGHT 档工作量（若把 STANDARD 也本地化，需 6–8 h/天）。**把 LIGHT 档（约占总 token 量的 60%）全部移到本地，云端只保留 STANDARD + DEEP，月支出可从 $177 降到 $70–90**。这正好落在建议预算内，且数据不出本地（PRD 24.3 的额外价值）。

**本地模型不适合 TIER_DEEP**（PRD 24.3 已指出）：推理深度不足，日报/周报的复杂复盘仍需云端。

#### 4.3.2 备份占用

27.4 要求每日 `pg_dump` + 保留 14 天 + 每季度恢复演练：

```

14 天滚动 ≈ 120–140 GB  ← 容易被忽略的磁盘占用
```

**建议**：备份单独用一个卷，或改用增量备份（`pgBackRest` / WAL 归档）——保留 14 天全量在第 3 年会吃掉 100 GB+，与"原始数据才 90 GB"完全不成比例。**备份策略必须显式包含备份自身的容量规划**（PRD 27.4 未涉及这一点）。

### 4.6 交易成本假设（用于轨道 B，非真实支出）

项目为 Dry-run，**不产生真实交易费用**。但轨道 B（经济性评估）必须用真实费率，否则「判断对但亏钱」会被归因错误（25.1）。

| 项 | 现货 | USDⓈ-M 永续（VIP0） |
|---|---|---|
| Maker | 0.100% | **0.020%** |
| Taker | 0.100% | **0.050%** |
| BNB 支付折扣 | -25% | -10% |
| 一次往返（按 taker） | 0.200% | **0.100%** |
| 一次往返（按 maker） | 0.200% | 0.040% |
| 计费基数 | 成交额 | **仓位名义价值**（非保证金） |

**Funding**：永续每 8 小时结算一次，方向不利方支付，费率随多空拥挤度浮动（常见区间 ±0.01%，极端可到 ±0.1%）。必须按 `funding_accrual_id` 逐笔幂等入账（25.4）。

**滑点**：无真实成交，只能假设。PRD 25.4 要求记录假设模型与实际成交价的差异；首期建议固定假设 + 三档敏感度（×0.5 / ×1 / ×2，25.3）。

**成本敏感性提醒**：永续一次往返 taker 成本 0.10%，若策略平均持仓 4 小时、目标收益 0.3%，成本占比 33%——**成本假设的乐观或悲观会直接翻转结论**。这正是 25.4 要求「按 Freqtrade 实际使用的 maker/taker 费率，不使用乐观假设」的原因。
