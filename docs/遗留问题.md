## 一、阻断级（会导致数据错误或功能不可用）

### L-01 SPOT 市场会误拉衍生品数据 ✅ 已修复（2026-11-24）

> **修复摘要**：新增 `MARKET_CAPABILITIES` 能力表 + `supports()` 判定函数；
> client 层加 `_get_supported()` 守卫（发请求前拦截，抛
> `UnsupportedMarketError`）；collector 按能力**不排期**衍生品轮询，
> 且现货不订阅 `markPrice` 流；`_guard` 单独捕获
> `UnsupportedMarketError`，不再累加 `_rest_failures`。
> 回归测试见 `tests/unit/test_market_capabilities.py`（16 项）。

- **原始现象**：`derivatives_collector.py` 对每个 `market_type` 都执行全套轮询，包括
  持仓量、资金费率、OI 历史。但这些是**衍生品专属**数据，现货市场没有。
  `binance_derivatives.py` 里 `OI_PATH` / `FUNDING_RATE_PATH` /
  `PREMIUM_INDEX_PATH` / `OI_HISTORY_PATH` **全部是 `/fapi/` 路径**，
  与 `BASE_URLS["SPOT"]`（`api.binance.com`）拼接后会形成无效 URL。
- **影响**：
  - 现货 collector 持续发起注定失败的请求。实测 `api.binance.com/fapi/v1/openInterest`
    与 `/fapi/v1/fundingRate` 均返回 **403**（不是超时），请求会立刻失败，
    但每次都要消耗限流配额；
  - **会污染质量事件表**：403 走 `raise_for_status()` 抛 `httpx.HTTPStatusError`
    → 被 `_guard` 捕获并累加 `_rest_failures` → 连续 3 次后触发
    `_record_stale()`，往 `market_data_quality_events` 写入
    **CRITICAL / STALE** 事件。这些事件**不是真实的数据质量问题**，
    而是「现货市场本来就没有衍生品数据」导致的必然失败；
  - 现货的 `markPrice@1s` 流不存在（该流仅 USDⓈ-M 有），WS 订阅无意义。
- **数据不会串**（已实测确认）：`parse_open_interest` 等解析函数的 `market_type`
  是**显式传入**的，即使端点返回了可用响应，落库时也会正确标记为 `SPOT`，
  不会把期货数据标成现货。真正的问题是**虚假的质量告警**而非数据污染。
- **当前缓解**：`config/base.toml` 的 `market_types` 含 `SPOT`，
  但 `.env` 通常只跑 `--market-types USDM_FUTURES`（脚本默认读 `MARKET_TYPES`，
  **默认包含 SPOT**）。
- **建议修复**：在 `DerivativesCollector` 中按 `market_type` 分流——
  - `USDM_FUTURES`：全量（OI / funding / markPrice / 盘口 / 成交）；
  - `SPOT`：仅盘口深度 + 聚合成交（基差计算需要现货报价，见 29.6）。
  端点路径也需按市场选择，不能只按 base URL 切换。
- **PRD 依据**：29.2.1（订阅清单按 `symbol × market_type` 区分）、
  29.6（基差需现货与期货双侧）。
- **修复后的行为**（已用 mock transport 实测）：
  - 现货 collector 只发出**盘口深度**请求，OI / funding / premiumIndex
    在 HTTP 层之前就被拦截，请求数从 4 降到 1；
  - 现货的 WS URL 不含 `markPrice`，期货仍包含；
  - `UnsupportedMarketError` 走 `_guard` 的独立分支，不产生质量事件。

### L-02 资金费率陈旧阈值定义但从未使用 ✅ 已修复（2026-11-24）

> **修复摘要**：按 PRD 29.4.3 实现**两条**独立的陈旧判定——
> `_check_funding_history_staleness()`（REST 轮询，`funding_time` vs 拉取时刻，
> 阈值 8 小时）与 `_check_funding_current_staleness()`（WS `markPrice` 流，
> 「多久没收到新推送」，阈值 2 分钟）。
> `build_stale_event()` 新增 `detected_by` 参数以区分 `REST` / `WS`。
> 回归测试见 `tests/unit/test_derivatives_funding_staleness.py`（14 项）。

- **原始现象**：`derivatives_collector.py` 定义了
  `FUNDING_STALE_THRESHOLD_SECONDS = 120.0`（29.4.3：资金费率当前值允许滞后 2 分钟）
  与 `FUNDING_HISTORY_STALE_THRESHOLD_SECONDS = 8 * 3600.0`（历史允许 1 个周期），
  但**两个常量都没有任何调用点**。全仓 grep 仅命中定义处与 `__all__`。
- **影响**：资金费率数据陈旧时**不会**产生 `DATA_STALE` 质量事件。
  只有 OI 走通了 `_check_oi_staleness`。
  下游按 29.4.3 判定「资金费率是否可信」时缺少依据；
  PRD 29.4.3 的表格明确要求 `funding_rate` 当前值超 2 分钟即判 `DATA_STALE`。
- **修复要点**：
  - 两条判定的**语义不同**，不能合并：
    - `funding_history` 是 REST 轮询数据 → 比对「业务时间 `funding_time`
      vs 拉取时刻」，超过 1 个周期（8h）说明**已错过一次结算**；
    - `funding_rate` 当前值来自 WS `markPrice` 流（1 秒推送）→
      「陈旧」实际含义是「**已多久没收到新消息**」，是 WS 断流/半开信号，
      而非单条消息的业务时间陈旧。
  - 当前值判定挂在轮询循环上，间隔 30 秒
    （`FUNDING_CURRENT_CHECK_INTERVAL_SECONDS`）——显著小于 2 分钟阈值，
    又不至于给质量事件表刷重复记录；
  - **从未收到过** `markPrice` 时**不写事件**：WS 尚未建立或刚断流时，
    断流本身由 `_ws_loop` 的重连逻辑与 `market_monitor` 负责，
    避免同一故障写两条事件；
  - `detected_by` 区分 `REST`（轮询类）与 `WS`（当前值），
    两者都走通路 C，但排障时需要区分来源。
- **真库实测**（Postgres 16 容器）：
  - funding 历史陈旧 → 落库 `DATA_STALE / CRITICAL / STALE / by=REST`，
    `staleness_seconds=32400.0 > threshold=28800.0`；
  - funding 当前值陈旧 → 落库 `by=WS`，
    `staleness_seconds=180.0 > threshold=120.0`；
  - 未超限的那次**未产生**事件（不刷噪声）。

### L-15 `.env.example` 模板复制出来无法启动 ✅ 已修复（2026-11-24）

> **修复摘要**：在 `Settings` 增加 `mode="before"` 的模型校验器
> `_blank_optional_to_none()`——把**可空字段**（`X | None`）的空字符串
> 归一化为 `None`；必填字段留空仍然报错。
> 回归测试见 `tests/unit/test_settings_env_example.py`（14 项）。

- **原始现象**：按 PRD 32.2 的约定，`.env.example` 对未配置项**留空**
  （敏感项也必须留空）。但把这个文件原样复制成 `.env` 后，
  **进程无法启动**：
  ```
  pydantic_core._pydantic_core.ValidationError: 3 validation errors for Settings
  LLM_ENABLE_THINKING
    Input should be a valid boolean, unable to interpret input [type=bool_parsing, input_value='', input_type=str]
  LLM_DAILY_TOKEN_BUDGET
    Input should be a valid integer, unable to parse string as an integer
  LLM_DAILY_COST_BUDGET_USD
    Input should be a valid number, unable to parse string as a number
  ```
  直接导致 `alembic upgrade` 与后端启动全部失败。
- **影响**：**新人第一步就会卡住**。`.env.example` 是配置体系的门面
  （32.2 明确要求包含全部配置项），但它实际不可用。
  这类问题在 CI 里测不出来——CI 直接在 `env:` 段里写死环境变量，
  从不加载 `.env` 文件。
- **修复要点**：
  - **只对可空字段做归一化**。用 `get_origin` / `get_args` 判断注解里
    是否含 `NoneType` 联合成员，区分「未配置」与「配置了但非法」：
    - 可空字段留空 → `None`（= 未配置，符合 32.2 语义）
    - 必填字段留空 → 仍然报错（真正的配置缺失，必须显式暴露，32.3）
    - 非空但非法的值 → 仍然报错（不能被归一化掩盖）
  - 归一化在 `mode="before"` 的 `model_validator` 中做，
    早于字段类型校验，因此空串不会先撞上 `bool` / `int` / `float` 解析器。
  - 只处理**字符串**空值；`"0"` 这类「看起来像空」的值按字面量解析。
- **实测**：按模板复制 → 只填 `DATABASE_URL` / `REDIS_URL` → 迁移成功、
  后端 `/ready` 返回 `database: ok, redis: ok`。

  - **为什么用 Redis**：采集器（`run_derivatives_collector.py`）与

  - Decimal 以**字符串**序列化（30.2：不经浮点中转）。

  - 键 `market:funding_current:USDM_FUTURES:BTCUSDT`，TTL 实测 360 秒；

### L-06 多空偏向与价格/OI 背离永远无法产出 ✅ 已修复（2026-11-24）

> **修复摘要**：新增 `market.price_change_pct()` 加载已收盘 K 线的收盘价变化率，

- **原始现象**：`domain/market/derivatives.py` 的 `long_short_skew()` 接收

  ```python

      oi_change=oi_change,
      funding_rate=funding_rate,
      price_change_pct=None,   # <- 恒为 None
  ```

- **更严重**：领域层已实现 `price_oi_divergence(price_change_pct, oi_change)`，

  - **价格与 OI 必须同源同窗口**：价格取**期货侧** 1h K 线（OI 也来自期货侧），

  - **口径与 OI 对齐**：领域层 `oi_change_pct()` 的窗口起点是

    **最新已收盘 K 线**为终点往回取，两者覆盖同一段时间；
  - **只使用已收盘 K 线**（29.5），未收盘 K 线参与判定会产生假异动；
  - 价格用 `Decimal` 直接算，不经浮点中转（30.2）。

  | 价格跌 + OI 跌 | -5.26% | -9.09% | ✅ false |

#### 实现的规则族（PRD 22.2.4）

| 规则 ID | 触发条件 | 级别 | 缺失数据行为 |
| --- | --- | --- | --- |
| `DER_OI_SURGE` | 1h OI 变化率 ≥ +3.0% | WARN | skipped |
| `DER_OI_SURGE_CRIT` | 1h OI 变化率 ≥ +6.0% | CRITICAL | skipped |
| `DER_OI_FLUSH` | 1h OI 变化率 ≤ −3.0% | CRITICAL | skipped |
| `DER_FUNDING_EXTREME` | \|funding\| ≥ 0.05% | WARN / CRITICAL | skipped |
| `DER_FUNDING_FLIP` | funding 穿越 0 零点 | INFO | skipped |
| `DER_BASIS_EXTREME` | \|basis\| ≥ 历史 P95 | WARN | skipped |
| `DER_LS_SKEW` | 多空拥挤分位 ≥P95 或 ≤P5 | WARN | skipped |
| `DER_PRICE_OI_DIVERGENCE` | 价格与 OI 反向且双向超阈值 | WARN | skipped |

#### 关键设计决策

1. **缺失数据绝不当作 0**
   所有取数函数在数据缺失时返回 `None`，对应规则计入 `skipped`。
   若按 0 处理：`DER_OI_FLUSH`（−3%）会在数据缺失时**误报崩塌**，
   `DER_FUNDING_EXTREME` 会**漏报**费率极端。

2. **方向性判定**
   `DER_OI_SURGE` 只看**上升**，`DER_OI_FLUSH` 只看**下降**——
   两者是相反方向的事件，不能共用「绝对值」判定。
   崩塌用 **WARN 阈值**（−3%）而非 CRITICAL 阈值（−6%）：−3% 就是崩塌信号。

3. **配置版本分离（PRD 30.6）**
   新增 `rule_version_for(rule_id)`：**每条规则行绑定它自己的阈值版本**。
   v1 的价格/波动/成交量规则阈值未变，仍属 v1；只有新增的 `DER_*` 属 v2。
   若一律用「当前版本」，旧规则会引用不存在的版本行 → **外键违例**。

4. **禁用判定方向修正**
   原实现 `f"{rule_id}_CRIT" in disabled` 的方向是**反的**：
   禁用 `DER_FUNDING_EXTREME` 反而放行其 CRIT 变体。
   统一改为「去掉 `_CRIT` 后缀的基础 ID」口径。

5. **多空比的保守推断**
   Binance 的 `globalLongShortAccountRatio` 未被采集，多空比**不可直接观测**。
   这里用与领域层 `long_short_skew()` 一致的联合信号构造标量：
   资金费率符号（方向）+ OI 变化（确认扩张）。

- **影响**：
  - **成本完全不可见**：无法回答「这个月花了多少钱」「哪个 Agent 最贵」

  - **版本不可追溯**：无法回答「这条报告是哪一版模型 + 哪一版 Prompt 产出的」，

  - **不可逆的数据债**：token 数**只有供应商知道**，事后无法补。

- **修复要点**：

  1. **计量必须在「收到响应的当下」完成**，不能等报告生成完再补。
     `extract_usage()` 从响应里取 `usage.prompt_tokens` / `completion_tokens`；
     供应商不给 `usage` 时返回 `(0, 0)`——**不报错**
     （没有 usage 不代表调用失败），但也不假装有数据。

  2. **失败调用同样要记录**。失败也会消耗 token，
     漏记会让成本**系统性低估**。所有失败分支
     （HTTP 非 2xx / schema 校验失败 / 响应包络异常 / 传输异常）
     都写一行 `model_runs`。

  3. **单价缺失 ≠ 成本为 0**。`llm_cost_records.estimated_cost_usd` 是
     `NOT NULL`，单价缺失时只能写 0——但同时在 `price_snapshot` 里写
     **`"priced": false`** 显式标记「未定价」。
     绝不能让读者把 0 误读成「这次调用不花钱」。
     这与 L-05「键缺失 ≠ 费率为 0」是同一条原则。

  4. **单价快照随成本落库**。`price_snapshot` 存**当时生效**的单价
     （含 `pricing_version`），而不是按当前单价表回查。
     改了单价表，历史成本不会漂移；缺了单价表，历史成本依然可复算。

  5. **Prompt 版本从文件名解析**。版本号写在文件名（`analysis.v1.md`）
     而非内容里——写在内容里会产生「改了内容但忘了改版本号」的漂移，
     而文件名在版本控制里，改内容时 diff 一眼可见。

  6. **哈希基于原始字节**。换行符归一化（CRLF vs LF）会让同一份内容
     算出两个哈希，「同一版本」在审计时看起来像两个版本。

  7. **缺占位符必须报错**。`PromptTemplate.render()` 遇到未提供的占位符
     直接抛错——若静默保留 `{schema}` 字面量发给模型，
     模型会把占位符当正文。

  8. **指定版本不存在时必须报错**，不回落「最大版本」。
     静默回落会让「v2 不存在」变成「用 v1 跑」——
     这正是 L-07a「阈值回落硬编码默认值」那类静默失效。

  9. **计量与报告同事务**。`process_one()` 里

### L-17 并发登记 Prompt 版本会撞唯一约束，导致分析任务全灭 ✅ 已修复（2026-11-25）

> **发现于**：L-16 修复后的**二次验证**阶段（真实 HTTP 端到端 + 并发压测）。
> 单线程下 793 个测试**全绿**，但生产的多 worker 场景会 100% 失败。

- **原始现象**：3 个 worker 并发处理 3 个分析任务，
  三个任务**全部**落到 `FAILED`，错误是
  `IntegrityError: duplicate key value violates unique constraint "pk_prompt_versions"`。
  单个 worker 单独跑则完全正常。

- **根因**：`register_prompt_version()` 用「**先查再插**」（TOCTOU 竞态）：

  ```python
  existing = db.execute(select(PromptVersion).where(...)).scalar_one_or_none()
  if existing is not None:
      return
  db.add(PromptVersion(...))   # ← 并发时大家一起走到这里
  ```

  `prompt_versions` 的主键是 `(agent_name, prompt_version)` 组合。
  多个 worker 并发时**都查不到**（都还没提交），于是**都执行插入**，
  第二个开始就撞唯一约束 → 整个事务回滚 → 任务被判 `LLM_SCHEMA_INVALID`。

- **为什么单测抓不到**：「先查再插」在单线程下**永远是对的**
  （查到就 return），所以常规单测、乃至并发度为 1 的集成测试都全绿。
  竞态窗口只在**真并发**下出现，必须用 `threading.Barrier` 让所有线程
  在同一时刻冲进那个窗口才稳定复现。

- **修复**：改用 PostgreSQL 原生 upsert，把「查+插」压成**一条原子语句**：

  ```python
  pg_insert(PromptVersion).values(...).on_conflict_do_nothing(
      index_elements=["agent_name", "prompt_version"]
  )
  ```

  `sync_model_pricing()` 里有**同型**的「先查再插」，一并改成
  `on_conflict_do_nothing().returning(...)`——既原子，又能靠
  `RETURNING` 判断「这行是不是我插进去的」，从而**保留**「同版本单价变了
  必须报错」的版本纪律。

- **回归保障**：`tests/integration/test_llm_metering_concurrency.py`
  两项测试均经「**回退修复 → 确认测试失败 → 恢复修复 → 确认通过**」
  验证过有效性（详见该文件顶部说明）。

> **教训**：**幂等写入不等于并发安全**。「先查再插」写起来像幂等，
> 在单线程下也确实幂等，但它在并发下是**竞态**。
> 涉及唯一约束的写入，一律用数据库原生的 upsert
> （`ON CONFLICT DO NOTHING` / `DO UPDATE`），
> 不要用「查一下再决定写不写」。

### L-18 空 Prompt 模板不会被拒绝，白白消耗一次模型调用 ✅ 已修复（2026-11-25）

> **发现于**：L-16 修复后的**失败模式验证**阶段。

- **原始现象**：`load_template()` 对**内容为空**（0 字节或纯空白）的
  `.md` 文件照常加载，`template_hash` 也能算出来。
  这类模板一旦被误提交（比如 `git add` 时新建了空文件），
  worker 会拿着一个**空 system prompt** 去调模型：
  白白消耗一次调用（真实计费），产出一份必然 schema 校验失败的报告。

- **修复**：加载时直接拒绝空模板，抛 `PromptVersionError`：

  ```python
  if not raw.strip():
      raise PromptVersionError(f"Prompt 模板 {path} 内容为空")
  ```

  失败得**早一点、清楚一点**，比浪费一次计费调用再报
  「LLM_SCHEMA_INVALID」好得多——后者完全指不出真正原因是模板空了。

- **回归保障**：`tests/unit/test_prompt_loading.py` 两项
  （`test_empty_template_rejected` / `test_zero_byte_template_rejected`）。

> **教训**：**「能加载出来」不等于「内容有效」**。
> 配置文件/模板的加载器要校验**内容本身**，而不只是**路径能不能找到**。

> **教训**：与 L-07a 同源——**「表建好了」不等于「有人在用」**。
> 判断一项配置或一张表是否真的生效，要 grep **消费方**而不是**定义方**。
> 这次的三个缺口（表、Prompt、单价段）全部是「定义完整、消费方为零」，
> 若不做全仓 grep 交叉核对，仅看目录结构完全看不出问题。

- **实测**：真实 HTTP 服务端验证 16/16——503 重试成功、输入超限
  服务端收到 **0 个请求**、修复请求**不含快照但含上一次的输出与错误**。

### L-14 Docker 服务必须用 `127.0.0.1` 而非 `localhost` 连接 ✅ 已验证

- **现象**：集成测试「挂起」不结束——`create_engine()` 卡在 `connect`，
  单个测试耗时 131 秒才通过（此前全量仅需 13 秒）。
  逐步二分定位到 TCP 层：
  - `127.0.0.1:5432` → 连接耗时 **0.01s**（正常）；
  - `localhost:5432` → 连接耗时 **8~20s**（每次都触发 `connect_timeout`）。
- **根因**：Windows 的 `localhost` 同时解析出 **IPv6 `::1`**（AAAA 记录，优先）
  与 IPv4 `127.0.0.1`。Docker Desktop 发布的端口**只监听 IPv4**，
  因此 IPv6 连接会挂起直到超时，再回退到 IPv4——
  表现就是「每次连接都慢一个超时周期」，而不是直接报错。
  操作系统 hosts 文件里 `::1 localhost` 已被注释，
  解析结果由 DNS 提供。
- **影响**：
  - 本地跑集成测试时，**每个数据库连接**都会白等一个超时周期，
    17 个集成测试累积起来就是十几分钟，且**不报错**、只是极慢，
    极易被误判为「测试死锁」或「代码性能问题」；
  - 真实配置**已经是正确的**：`.env` 与 CI 都用 `127.0.0.1`，
    因此**不影响 CI，也不影响正常开发流程**；
  - 但任何临时用 `localhost` 拼连接串的命令或脚本都会踩坑。
- **建议**：
  - 本地临时起服务时，连接串统一写 `127.0.0.1`（`.env.example` 已如此）；
  - 若使用 `localhost`，需确保 Docker 侧也发布 IPv6，或在 hosts 中
    显式把 `localhost` 指向 `127.0.0.1`；
  - **排查提示**：连接慢但最终成功 → 先比对 `127.0.0.1` 与 `localhost`
    的耗时差异，而不是怀疑数据库负载或代码死锁。
