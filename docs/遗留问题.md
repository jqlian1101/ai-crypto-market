## 一、阻断级（会导致数据错误或功能不可用）

### L-01 SPOT 市场会误拉衍生品数据 ✅ 已修复（2026-11-24）

> **修复摘要**：新增 `MARKET_CAPABILITIES` 能力表 + `supports()` 判定函数；
> client 层加 `_get_supported()` 守卫（发请求前拦截，抛
> `UnsupportedMarketError`）；collector 按能力**不排期**衍生品轮询，
> 且现货不订阅 `markPrice` 流；`_guard` 单独捕获
> `UnsupportedMarketError`，不再累加 `_rest_failures`。
> 回归测试见 `tests/unit/test_market_capabilities.py`（16 项）。

- **原始现象**：`derivatives_collector.py` 对每个 `market_type` 都执行全套轮询，包括
  持仓量、资金费率、OI 历史。但这些是**衍生品专属**数据，现货市场没有。
  `binance_derivatives.py` 里 `OI_PATH` / `FUNDING_RATE_PATH` /
  `PREMIUM_INDEX_PATH` / `OI_HISTORY_PATH` **全部是 `/fapi/` 路径**，
  与 `BASE_URLS["SPOT"]`（`api.binance.com`）拼接后会形成无效 URL。
- **影响**：
  - 现货 collector 持续发起注定失败的请求。实测 `api.binance.com/fapi/v1/openInterest`
    与 `/fapi/v1/fundingRate` 均返回 **403**（不是超时），请求会立刻失败，
    但每次都要消耗限流配额；
  - **会污染质量事件表**：403 走 `raise_for_status()` 抛 `httpx.HTTPStatusError`
    → 被 `_guard` 捕获并累加 `_rest_failures` → 连续 3 次后触发
    `_record_stale()`，往 `market_data_quality_events` 写入
    **CRITICAL / STALE** 事件。这些事件**不是真实的数据质量问题**，
    而是「现货市场本来就没有衍生品数据」导致的必然失败；
  - 现货的 `markPrice@1s` 流不存在（该流仅 USDⓈ-M 有），WS 订阅无意义。
- **数据不会串**（已实测确认）：`parse_open_interest` 等解析函数的 `market_type`
  是**显式传入**的，即使端点返回了可用响应，落库时也会正确标记为 `SPOT`，
  不会把期货数据标成现货。真正的问题是**虚假的质量告警**而非数据污染。
- **当前缓解**：`config/base.toml` 的 `market_types` 含 `SPOT`，
  但 `.env` 通常只跑 `--market-types USDM_FUTURES`（脚本默认读 `MARKET_TYPES`，
  **默认包含 SPOT**）。
- **建议修复**：在 `DerivativesCollector` 中按 `market_type` 分流——
  - `USDM_FUTURES`：全量（OI / funding / markPrice / 盘口 / 成交）；
  - `SPOT`：仅盘口深度 + 聚合成交（基差计算需要现货报价，见 29.6）。
  端点路径也需按市场选择，不能只按 base URL 切换。
- **PRD 依据**：29.2.1（订阅清单按 `symbol × market_type` 区分）、
  29.6（基差需现货与期货双侧）。
- **修复后的行为**（已用 mock transport 实测）：
  - 现货 collector 只发出**盘口深度**请求，OI / funding / premiumIndex
    在 HTTP 层之前就被拦截，请求数从 4 降到 1；
  - 现货的 WS URL 不含 `markPrice`，期货仍包含；
  - `UnsupportedMarketError` 走 `_guard` 的独立分支，不产生质量事件。

### L-02 资金费率陈旧阈值定义但从未使用 ✅ 已修复（2026-11-24）

> **修复摘要**：按 PRD 29.4.3 实现**两条**独立的陈旧判定——
> `_check_funding_history_staleness()`（REST 轮询，`funding_time` vs 拉取时刻，
> 阈值 8 小时）与 `_check_funding_current_staleness()`（WS `markPrice` 流，
> 「多久没收到新推送」，阈值 2 分钟）。
> `build_stale_event()` 新增 `detected_by` 参数以区分 `REST` / `WS`。
> 回归测试见 `tests/unit/test_derivatives_funding_staleness.py`（14 项）。

- **原始现象**：`derivatives_collector.py` 定义了
  `FUNDING_STALE_THRESHOLD_SECONDS = 120.0`（29.4.3：资金费率当前值允许滞后 2 分钟）
  与 `FUNDING_HISTORY_STALE_THRESHOLD_SECONDS = 8 * 3600.0`（历史允许 1 个周期），
  但**两个常量都没有任何调用点**。全仓 grep 仅命中定义处与 `__all__`。
- **影响**：资金费率数据陈旧时**不会**产生 `DATA_STALE` 质量事件。
  只有 OI 走通了 `_check_oi_staleness`。
  下游按 29.4.3 判定「资金费率是否可信」时缺少依据；
  PRD 29.4.3 的表格明确要求 `funding_rate` 当前值超 2 分钟即判 `DATA_STALE`。
- **修复要点**：
  - 两条判定的**语义不同**，不能合并：
    - `funding_history` 是 REST 轮询数据 → 比对「业务时间 `funding_time`
      vs 拉取时刻」，超过 1 个周期（8h）说明**已错过一次结算**；
    - `funding_rate` 当前值来自 WS `markPrice` 流（1 秒推送）→
      「陈旧」实际含义是「**已多久没收到新消息**」，是 WS 断流/半开信号，
      而非单条消息的业务时间陈旧。

  - `detected_by` 区分 `REST`（轮询类）与 `WS`（当前值），
    两者都走通路 C，但排障时需要区分来源。
- **真库实测**（Postgres 16 容器）：
  - funding 历史陈旧 → 落库 `DATA_STALE / CRITICAL / STALE / by=REST`，

### L-06 多空偏向与价格/OI 背离永远无法产出 ✅ 已修复（2026-11-24）

> **修复摘要**：新增 `market.price_change_pct()` 加载已收盘 K 线的收盘价变化率，
> 并在 `build_derivatives()` 中接入：
> `detected` 改用领域层 `price_oi_divergence()` 真实计算（不再是手写字面量 `False`），
> `long_short_skew()` 也拿到真实价格变化率（不再是恒传 `None`）。
> 快照同时输出 `price_change_pct` / `oi_change_pct` / `price_window` 便于排障。
> 回归测试见 `tests/unit/test_price_oi_divergence_wiring.py`（24 项）。

- **原始现象**：`domain/market/derivatives.py` 的 `long_short_skew()` 接收
  `price_change_pct` 参数，但 `derivatives_snapshot.py` 调用时**恒传 `None`**：
  ```python
  "long_short_skew": long_short_skew(
      oi_change=oi_change,
      funding_rate=funding_rate,
      price_change_pct=None,   # <- 恒为 None
  ),
  ```
- **更严重**：领域层已实现 `price_oi_divergence(price_change_pct, oi_change)`，
  但**全仓没有任何调用点**（只在其定义处与 `__all__` 出现）。
  快照里的 `price_oi_divergence.detected` 是**手写的字面量 `False`**，
  不是计算结果。
- **影响**：多空偏向与价格/OI 背离这两项衍生品信号**永远无法真正产出**。
  PRD 22.2.4 的 `DER_LS_SKEW` 与 `DER_PRICE_OI_DIVERGENCE` 都依赖这个值。
  注意 `long_short_skew` 传 `None` 时返回 `NEUTRAL`——**不会报错**，
  属于静默失效：快照看起来正常，但信号恒为中性。
- **修复要点**：
  - **价格与 OI 必须同源同窗口**：价格取**期货侧** 1h K 线（OI 也来自期货侧），
    窗口统一为 1h（`OI_CHANGE_WINDOW_SECONDS`），
    否则「价格/OI 背离」是在比较两个不同量纲的区间；

    1h 周期 + 1h 窗口时，最新那根的 `close_time` 恰好等于 `as_of - 1h`，
    被严格大于号排除，只剩一根无法比较。改为按
    `窗口 / 周期 + 1` 根取数（1h 周期 + 1h 窗口 → 2 根）；
  - **口径与 OI 对齐**：领域层 `oi_change_pct()` 的窗口起点是
    「`<= 最新点 - window` 的最后一个采样点」，价格侧同样以
    **最新已收盘 K 线**为终点往回取，两者覆盖同一段时间；
  - **只使用已收盘 K 线**（29.5），未收盘 K 线参与判定会产生假异动；
  - 价格用 `Decimal` 直接算，不经浮点中转（30.2）。
- **真库实测**（Postgres 16，四组场景）：

  | 场景 | 价格变化 | OI 变化 | `detected` |
  |---|---|---|---|
  | 价格跌 + OI 涨 | -5.26% | +9.09% | ✅ **true** |
  | 价格涨 + OI 涨 | +4.76% | +9.09% | ✅ false |
  | 价格跌 + OI 跌 | -5.26% | -9.09% | ✅ false |
  | 价格跌 + OI 涨（幅度较小） | -5.26% | +4.76% | ✅ **true** |

  修复前 `detected` **恒为 false**。

#### 实现的规则族（PRD 22.2.4）

| 规则 ID | 触发条件 | 级别 | 缺失数据行为 |
| --- | --- | --- | --- |
| `DER_OI_SURGE` | 1h OI 变化率 ≥ +3.0% | WARN | skipped |
| `DER_OI_SURGE_CRIT` | 1h OI 变化率 ≥ +6.0% | CRITICAL | skipped |
| `DER_OI_FLUSH` | 1h OI 变化率 ≤ −3.0% | CRITICAL | skipped |
| `DER_FUNDING_EXTREME` | \|funding\| ≥ 0.05% | WARN / CRITICAL | skipped |
| `DER_FUNDING_FLIP` | funding 穿越 0 零点 | INFO | skipped |
| `DER_BASIS_EXTREME` | \|basis\| ≥ 历史 P95 | WARN | skipped |
| `DER_LS_SKEW` | 多空拥挤分位 ≥P95 或 ≤P5 | WARN | skipped |
| `DER_PRICE_OI_DIVERGENCE` | 价格与 OI 反向且双向超阈值 | WARN | skipped |

#### 关键设计决策

1. **缺失数据绝不当作 0**
   所有取数函数在数据缺失时返回 `None`，对应规则计入 `skipped`。
   若按 0 处理：`DER_OI_FLUSH`（−3%）会在数据缺失时**误报崩塌**，
   `DER_FUNDING_EXTREME` 会**漏报**费率极端。

2. **方向性判定**
   `DER_OI_SURGE` 只看**上升**，`DER_OI_FLUSH` 只看**下降**——
   两者是相反方向的事件，不能共用「绝对值」判定。
   崩塌用 **WARN 阈值**（−3%）而非 CRITICAL 阈值（−6%）：−3% 就是崩塌信号。

3. **配置版本分离（PRD 30.6）**
   新增 `rule_version_for(rule_id)`：**每条规则行绑定它自己的阈值版本**。
   v1 的价格/波动/成交量规则阈值未变，仍属 v1；只有新增的 `DER_*` 属 v2。
   若一律用「当前版本」，旧规则会引用不存在的版本行 → **外键违例**。

4. **禁用判定方向修正**
   原实现 `f"{rule_id}_CRIT" in disabled` 的方向是**反的**：
   禁用 `DER_FUNDING_EXTREME` 反而放行其 CRIT 变体。
   统一改为「去掉 `_CRIT` 后缀的基础 ID」口径。

5. **多空比的保守推断**
   Binance 的 `globalLongShortAccountRatio` 未被采集，多空比**不可直接观测**。
   这里用与领域层 `long_short_skew()` 一致的联合信号构造标量：
   资金费率符号（方向）+ OI 变化（确认扩张）。

- **影响**：
  - **成本完全不可见**：无法回答「这个月花了多少钱」「哪个 Agent 最贵」
    「哪一版 Prompt 最烧 token」；
  - **版本不可追溯**：无法回答「这条报告是哪一版模型 + 哪一版 Prompt 产出的」，
    这直接阻断 P7 的评估分组（按 Prompt 版本对比效果）；
  - **不可逆的数据债**：token 数**只有供应商知道**，事后无法补。
    每过一次没有计量的调用，就永久丢失一段成本历史。

- **修复要点**：

  1. **计量必须在「收到响应的当下」完成**，不能等报告生成完再补。

     供应商不给 `usage` 时返回 `(0, 0)`——**不报错**
     （没有 usage 不代表调用失败），但也不假装有数据。

  2. **失败调用同样要记录**。失败也会消耗 token，
     漏记会让成本**系统性低估**。所有失败分支
     （HTTP 非 2xx / schema 校验失败 / 响应包络异常 / 传输异常）
     都写一行 `model_runs`。

  3. **单价缺失 ≠ 成本为 0**。`llm_cost_records.estimated_cost_usd` 是
     `NOT NULL`，单价缺失时只能写 0——但同时在 `price_snapshot` 里写
     **`"priced": false`** 显式标记「未定价」。
     绝不能让读者把 0 误读成「这次调用不花钱」。
     这与 L-05「键缺失 ≠ 费率为 0」是同一条原则。

  4. **单价快照随成本落库**。`price_snapshot` 存**当时生效**的单价

  5. **Prompt 版本从文件名解析**。版本号写在文件名（`analysis.v1.md`）

  6. **哈希基于原始字节**。换行符归一化（CRLF vs LF）会让同一份内容

### L-17 并发登记 Prompt 版本会撞唯一约束，导致分析任务全灭 ✅ 已修复（2026-11-25）

> **发现于**：L-16 修复后的**二次验证**阶段（真实 HTTP 端到端 + 并发压测）。
> 单线程下 793 个测试**全绿**，但生产的多 worker 场景会 100% 失败。

- **原始现象**：3 个 worker 并发处理 3 个分析任务，
  三个任务**全部**落到 `FAILED`，错误是
  `IntegrityError: duplicate key value violates unique constraint "pk_prompt_versions"`。
  单个 worker 单独跑则完全正常。

- **根因**：`register_prompt_version()` 用「**先查再插**」（TOCTOU 竞态）：

  ```python
  existing = db.execute(select(PromptVersion).where(...)).scalar_one_or_none()
  if existing is not None:
      return
  db.add(PromptVersion(...))   # ← 并发时大家一起走到这里
  ```

  `prompt_versions` 的主键是 `(agent_name, prompt_version)` 组合。
  多个 worker 并发时**都查不到**（都还没提交），于是**都执行插入**，
  第二个开始就撞唯一约束 → 整个事务回滚 → 任务被判 `LLM_SCHEMA_INVALID`。

- **为什么单测抓不到**：「先查再插」在单线程下**永远是对的**
  （查到就 return），所以常规单测、乃至并发度为 1 的集成测试都全绿。
  竞态窗口只在**真并发**下出现，必须用 `threading.Barrier` 让所有线程
  在同一时刻冲进那个窗口才稳定复现。

- **修复**：改用 PostgreSQL 原生 upsert，把「查+插」压成**一条原子语句**：

  ```python
  pg_insert(PromptVersion).values(...).on_conflict_do_nothing(
      index_elements=["agent_name", "prompt_version"]
  )
  ```

  `sync_model_pricing()` 里有**同型**的「先查再插」，一并改成
  `on_conflict_do_nothing().returning(...)`——既原子，又能靠
  `RETURNING` 判断「这行是不是我插进去的」，从而**保留**「同版本单价变了
  必须报错」的版本纪律。

- **回归保障**：`tests/integration/test_llm_metering_concurrency.py`
  两项测试均经「**回退修复 → 确认测试失败 → 恢复修复 → 确认通过**」
  验证过有效性（详见该文件顶部说明）。

> **教训**：**幂等写入不等于并发安全**。「先查再插」写起来像幂等，
> 在单线程下也确实幂等，但它在并发下是**竞态**。
> 涉及唯一约束的写入，一律用数据库原生的 upsert
> （`ON CONFLICT DO NOTHING` / `DO UPDATE`），
> 不要用「查一下再决定写不写」。

### L-18 空 Prompt 模板不会被拒绝，白白消耗一次模型调用 ✅ 已修复（2026-11-25）

> **发现于**：L-16 修复后的**失败模式验证**阶段。

- **原始现象**：`load_template()` 对**内容为空**（0 字节或纯空白）的

  这类模板一旦被误提交（比如 `git add` 时新建了空文件），
  worker 会拿着一个**空 system prompt** 去调模型：
  白白消耗一次调用（真实计费），产出一份必然 schema 校验失败的报告。

- **修复**：加载时直接拒绝空模板，抛 `PromptVersionError`：

  ```python

  ```

  失败得**早一点、清楚一点**，比浪费一次计费调用再报
  「LLM_SCHEMA_INVALID」好得多——后者完全指不出真正原因是模板空了。

  （`test_empty_template_rejected` / `test_zero_byte_template_rejected`）。

> **教训**：**「能加载出来」不等于「内容有效」**。
> 配置文件/模板的加载器要校验**内容本身**，而不只是**路径能不能找到**。

> **教训**：与 L-07a 同源——**「表建好了」不等于「有人在用」**。
> 判断一项配置或一张表是否真的生效，要 grep **消费方**而不是**定义方**。

> 若不做全仓 grep 交叉核对，仅看目录结构完全看不出问题。

  - **分层优化的收益完全落空**。全部流量按 STANDARD 计费。

  - **成本报表的 `tier` 列恒为 `TIER_STANDARD`**——分组能力有、
    数据没有，报表做不出分档结论。

  1. **档位必须显式落库**。落的是**实际生效**的档位（降级后可能低于

  2. **DEEP 绝不降级到 LIGHT**（PRD 24.1「不要降级这一档」）。
     拿 LIGHT 档的模型冒充 DEEP 的结果**比直接失败更糟**——

     至少显式的失败让人知道该去查什么。

  - **全部档位未配置模型时必须抛错**，不能「随便找个模型用」——

- **实测**：真实 HTTP 端到端 21/21——LIGHT 档请求体里的 `model`

> **教训**：与 L-19 / L-20 同源——**「配套设施齐全」最容易掩盖「关键一步没接上」**。
> 这次尤其值得记：枚举、CHECK 约束、文档、成本模型**全都对**，

### L-22 模型分层的本地优先分支绕过降级链，返回空模型名 ✅ 已修复（2026-11-25）

> **发现于**：P4 Phase 3 提交后的**二次验证**阶段（针对分层逻辑的
> 边界场景穷举）。单元测试 29 项与集成测试 9 项**全绿**，
> 但都只覆盖了「配置齐全」与「全部未配置」两类场景。

- **原始现象**：`prefer_local=True`（本地优先）且**本地模型未配置**时，
  路由解析**跳过了档位降级链**，直接返回目标档位的云端路由。
  由于此时目标档位往往也没配模型，结果是：
  - `model_id` 为**空字符串**（不是 `None`，是 `""`）；
  - 档位仍是请求的档位（`TIER_DEEP`），**没有任何降级标记**；
  - **全部档位都未配置时也不抛错**，静默返回一个空模型。

- **影响**：
  - **静默用错档位**（违反本项目自己定的铁律）：
    「所有档位均未配置模型」本该抛 `LLM_UNAVAILABLE`——
    静默用错档位比失败危险得多。实际却发出了一个 `model=""` 的请求。
  - **失败原因极难定位**。请求带着空的 `model` 字段发出去，
    供应商侧报「未知模型」，与本地 vs 云端、档位 vs 供应商的排查完全混在一起。
  - **降级链被绕过**：DEEP 未配、STANDARD 已配的情况下，
    本该降级到 STANDARD 继续跑，实际却拿到空模型名直接失败——
    **一个本可以成功的分析任务失败了**。

- **根因**：`prefer_local` 分支直接调用 `_cloud_route(settings, requested_tier)`，
  而 `_cloud_route` 里的 `model or model_for_tier(...) or ""`
  在两者皆空时**返回空字符串**。降级链在另一个函数里，
  本地优先分支**根本没调用它**。

- **修复**：把降级链抽成 `_resolve_cloud_route()`，
  **本地优先回退云端时也走它**，不再直接调 `_cloud_route()`。
  同时给 `_cloud_route` 加一道防御：**模型名为空直接抛
  `LLM_UNAVAILABLE`**，杜绝空字符串流出。

- **回归保障**：`tests/unit/test_tier_routing.py` 新增 3 项
  （共 32 项），锁死「本地未配 + 目标档位未配 -> 沿降级链降级」
  「本地未配 + 全部未配 -> 抛错」「任何可解析出的路由模型名不得为空」。

> **教训**：**「全部未配置时抛错」这条规则，只在主路径上被测过**。
> 同一个规则在**另一个分支**（本地优先）上根本没走降级链，
> 于是规则失效。**规则的验证必须覆盖每一条会走到它的路径**，
> 不能只验证「最典型的那条」。

### L-23 `prompt_versions` 主键缺模板名，user 模板登记被静默丢弃 ✅ 已修复（2026-11-25）

> **发现于**：新增「并发 + 重试」组合压测时，断言 Prompt 版本应登记 2 行，
> 实际只有 1 行。

- **原始现象**：`prompt_versions` 的主键是
  **`(agent_name, prompt_version)` 二元组**。但**同一个 Agent 下
  每个 Prompt 模板各有独立版本号**——

> **迁移里踩到的第三个坑（2026-11-25 二次验证发现）**：

> 结果 `.j2` 文件回填出 **`analysis.v1.j2`** 这种**带版本号的模板名**，
> 主键语义直接错了：**同一个模板的 `v1` 与 `v2` 会被当成两个不同的模板**——
> 恰好制造出本次修复要消灭的那类「该在的东西不在」。
> 已改为 `\\.(md|j2)$` 一并剥离。
>

> 全新库迁移正常**不代表**迁移正确。
> 而且回填逻辑此前**没有任何测试覆盖**，
> 只有真正造数据跑一遍 downgrade -> 塞数据 -> upgrade 才暴露。

> 测试直接**引用实现**而不是抄一份 SQL 副本——
> 否则改迁移时忘改测试，就会留下「测试全绿但迁移已经错了」的假象。

> **教训**：**「主键太粗」会让 `ON CONFLICT DO NOTHING`
> 从「防重复」变成「静默丢弃」**。原子 upsert 修好了并发，
> 却掩盖了主键定义本身的缺陷——
> **两个本来不同的东西，被当成了同一个**。
> 排查这类问题不能只看「有没有报错」，
> 要看**「该在的东西是不是都在」**：
> 断言只检查了 system 那一行，user 那行没了自然发现不了。

### L-24 计量记录随报告事务回滚销毁，成本报表系统性低估 ✅ 已修复（2026-11-25）

> **发现于**：P4「部分结果」（PRD 24.4）实现后的**事务边界**走查。
> 单元测试全绿、真库集成测试全绿——因为**它们都测不出回滚**。

- **原始现象**：`process_one()` 把「写计量」与「写报告」放在
  **同一个 `session_scope`** 里：

  ```python
  with session_scope(settings) as db:          # <- 一个事务
      content, model_id, prompt_version = generate_report(snapshot, settings, db=db)
      create_report(db, run_id=run_id, ...)
  ```

  `generate_report()` 在**模型调用失败时抛异常**，
  异常穿出 `session_scope` -> **整个事务回滚** ->
  **同事务里的 `model_runs` / `llm_cost_records` 一起消失**。

- **影响**：**失败尝试烧掉的 token 与费用从来没进过账本**。
  而且「越是在模型不稳定的时候低估得越多」——
  失败越多，账本缺得越多，**恰好是你最需要看清成本的时候**。
  这是**系统性低估**，不是随机噪声：成本报表看起来「很正常」，
  只是比真实值低，而且低得越来越多。

   960|  > **单元测试为什么测不出**：它们传一个 `db` session 进去、
   > 在**事务外**捕获异常——session 没被回滚，记录还在。
   > 必须让异常**穿过 `session_scope`** 才能暴露。

- **修复**：把**计量与报告拆成两个独立事务**：
  - 报告、运行状态走 `report_scope`；
  - **计量走独立的 `metering_scope`**，并给 `generate_report` 加
    `commit_metering` 参数，让**每一次 HTTP 尝试立刻提交**。

  关键点：**每一次尝试都单独提交**，而不是「整个分析任务提交一次」。
  这样即使 3 次尝试把进程搞崩了，**前 2 次的账也已经记上了**。

- **一个必须承认的代价**：拆分后可能出现「**有调用记录但没报告**」的状态。
  但那**恰恰是真实发生过的事**（调了、钱花了、报告没写成），
  **比悄悄抹掉更诚实**。原来的「原子性」看着漂亮，
  代价是**把已经发生的成本从账本里删掉**。

- **回归保障**：
  - `tests/integration/test_partial_result.py::test_metering_survives_transaction_rollback`
    ——让异常**穿过真实的 `session_scope`**，
    断言 2 次尝试（1 次 + 1 次重试）的计量**必须存活**；
  - `tests/integration/test_llm_retry_concurrency.py`——
    真并发 + 真重试下计量**不重不漏**。

> **教训**：**「同事务保证原子性」听起来总是对的，
> 但要先问一句「这个事务里有没有『已经发生的既成事实』」**。
> 成本、调用次数这类**外部世界的既成事实**，
> 与业务状态**不是一回事**——把它们绑在一个事务里，
> 业务回滚就会顺手把既成事实也回滚掉。
> 判据：**这件事发生了吗？** 发生了就**必须留痕**，
> 不能随业务事务一起消失。

### L-25 超时被误标为「模型调用失败」，降级原因与真实原因不符 ✅ 已修复（2026-11-25）

> **发现于**：L-24 修复后的**真实 HTTP 端到端验证**
> （起真实 socket 服务器，收下请求后故意不回应）。
> 单元测试与 MockTransport 测试**全部测不出**。

- **原始现象**：真实超时（`httpx.ReadTimeout`）触发后，
  报告里的 `degraded_reason` 写的是 **`MODEL_CALL_FAILED`**，
  而 `error_code` 是 **`LLM_TIMEOUT`**——**两者互相矛盾**。

- **根因**：`generate_report()` 把 `httpx.ReadTimeout`
  翻译成 `AICryptoError(LLM_TIMEOUT)` 抛出。
  而 `process_one()` 判定超时**只看异常类型**：

  ```python
  if isinstance(exc, (httpx.TimeoutException, TimeoutError)):
      code, status = ErrorCode.LLM_TIMEOUT, "TIMEOUT"
  ```

  **包过一层之后类型检查失配**——`AICryptoError` 不是 `httpx.TimeoutException`，
  于是超时被当成普通调用失败。

- **影响**：
  - **降级原因与真实原因不符**，运维按 `degraded_reason` 排查会去查
    「模型为什么报错」，而真实原因是「**上游卡住没响应**」——**查错方向**；
  - PRD 24.4 要求「输出『分析超时 + 已完成部分』」——
    连「这是超时」都没标对，**部分结果的主要用途就打了折扣**；
  - 监控上 `LLM_TIMEOUT` 与 `MODEL_CALL_FAILED` 混在一起，
    **无法区分「上游慢」与「上游报错」**——这两类的处置完全不同。

- **修复**：**同时按异常类型和错误码判定**：

  ```python
  if isinstance(exc, AICryptoError) and exc.code == ErrorCode.LLM_TIMEOUT:
      code, status = ErrorCode.LLM_TIMEOUT, "TIMEOUT"
  ```

- **回归保障**：
  - `tests/integration/test_partial_result.py::test_timeout_is_classified_as_timeout_not_call_failure`
    ——用**真正的 `httpx.ReadTimeout`**（不是 504 这类 HTTP 层错误）
    断言 `degraded_reason == "TIMEOUT"`；
  - `scripts/verify_partial_result_timeout.py`——真实 socket 端到端验证。

> **教训**：**「翻译层」会吃掉类型信息**。
> 一旦把底层异常包成领域异常，**基于 `isinstance` 的分类就失效了**。
> 领域异常应当**携带足够的信息让调用方能正确分类**——
> 判据是「调用方需要按这个信息做不同的处置吗」，
> 需要，就必须有；不要依赖「异常还能保持原类型」这种脆弱假设。

### L-14 Docker 服务必须用 `127.0.0.1` 而非 `localhost` 连接 ✅ 已验证

- **现象**：集成测试「挂起」不结束——`create_engine()` 卡在 `connect`，
  单个测试耗时 131 秒才通过（此前全量仅需 13 秒）。
  逐步二分定位到 TCP 层：
  - `127.0.0.1:5432` → 连接耗时 **0.01s**（正常）；
  - `localhost:5432` → 连接耗时 **8~20s**（每次都触发 `connect_timeout`）。
- **根因**：Windows 的 `localhost` 同时解析出 **IPv6 `::1`**（AAAA 记录，优先）
  与 IPv4 `127.0.0.1`。Docker Desktop 发布的端口**只监听 IPv4**，
  因此 IPv6 连接会挂起直到超时，再回退到 IPv4——
  表现就是「每次连接都慢一个超时周期」，而不是直接报错。
  操作系统 hosts 文件里 `::1 localhost` 已被注释，
  解析结果由 DNS 提供。
- **影响**：
  - 本地跑集成测试时，**每个数据库连接**都会白等一个超时周期，
    17 个集成测试累积起来就是十几分钟，且**不报错**、只是极慢，
    极易被误判为「测试死锁」或「代码性能问题」；
  - 真实配置**已经是正确的**：`.env` 与 CI 都用 `127.0.0.1`，
    因此**不影响 CI，也不影响正常开发流程**；
  - 但任何临时用 `localhost` 拼连接串的命令或脚本都会踩坑。
- **建议**：
  - 本地临时起服务时，连接串统一写 `127.0.0.1`（`.env.example` 已如此）；
  - 若使用 `localhost`，需确保 Docker 侧也发布 IPv6，或在 hosts 中
    显式把 `localhost` 指向 `127.0.0.1`；
  - **排查提示**：连接慢但最终成功 → 先比对 `127.0.0.1` 与 `localhost`
    的耗时差异，而不是怀疑数据库负载或代码死锁。

### L-27 去重键的 `revision` 写错，升级投递**每次扫描都重复投递** ✅ 已修复（2026-11-26）

> **发现于**：P4 收尾后的**通知投递链路走查**。
> 单元测试与集成测试**全绿**——因为它们测的都是「首投」路径，
> **没有任何一个用例覆盖「升级投递」**。

- **原始现象**：去重键的语义是 `(fingerprint, revision)`——
  同一事件的 **AI 解读升级投递**（`revision > 0`）是**另一次投递**，
  必须有自己的去重键。但 `mark_delivered` 写入时把 `revision`
  **硬编码成 0**，而检查侧读的却是 `event.revision`：

  ```
  写入: dedup:{fingerprint}:0
  检查: dedup:{fingerprint}:{event.revision}   # revision>0 时是另一个键
  ```

  升级投递因此会写下一个**永远不会被检查到**的键——
  下一轮扫描查不到「已投递」，于是**每次扫描都重新投递一遍**（通知轰炸）。
  与 L-05「键缺失 → 费率 0」、L-23「主键太粗会被 ON CONFLICT 静默丢弃」
  是同一族的**静默失效**：不报错，只是把该做的事没做。

- **修复要点**：

  1. `mark_delivered` 的 `revision` 提为**显式必填**参数，
     由调用方传入 `event.revision`；
  2. `load_delivered` 同步**去掉默认 `0`**，两侧口径一致
     （静默默认 `0` 会让升级投递用首投的键去查，
     查出「未投递」→ 重复投递——**默认值本身就是 bug 温床**）；
  3. **冷却键只在首投**（`revision == 0`）时写入——
     升级投递不占用冷却窗口（PRD 22.4.4.1 第 3 条）。

- **回归保障**：
  - `tests/unit/test_anomaly_state.py`（新增）锁死三条不变量：
    去重键的 `revision` 必须一致（写入后能用同一 `revision` 查回、
    用错 `revision` 必须查不到）、升级投递不占冷却窗口、
    去重键与冷却键空间互相独立；
  - `tests/unit/test_notification_dispatch.py` 新增 2 项，锁死
    投递链路必须把事件的 `revision` **原样**传给写去重键的调用方，
    且 `revision=0` 也必须**显式**传递（不给默认值，避免调用方漏传后静默走错键）。

> **教训**：**「默认值」是静默失效的高发区**。
> 与 L-25「按异常类型而非错误码判定」同源——
> **默认值让「忘了传」和「传错」长得一模一样**。
> 正确做法：**在语义需要区分的地方，禁止默认值**，把错误挡在编译期/调用期。

### L-28 集成测试大面积 skip：`.env` 里的测试库配置对 `os.getenv()` 无效 ✅ 已修复（2026-11-26）

> **发现于**：Windows 本机环境盘点（Python 版本统一到 3.13 时顺带全量跑测试）。
> 本机 Docker 容器 healthy、迁移已到 head、`.env` 一应俱全，
> 但 **71 个集成测试全部 skip**、另有 **2 个 error**。

- **原始现象（三个叠加的缺口）**：

  1. **`.env` 里的配置对 `os.getenv()` 无效**。
     集成测试一律用 `os.getenv("ANALYSIS_TEST_DATABASE_URL")` 取连接串，
     而 `.env` 是由 **pydantic-settings** 读取的——它把值灌进 `Settings`，
     **不写回 `os.environ`**。CI 之所以没这问题，是因为 CI 的 `env:` 段
     直接注入**进程环境变量**。本地缺的就是这一层。
     **开发者「明明配了却全 skip」的根因就在这里**，
     而且它**不会让任何测试失败**——只是安静地少跑了几十个真库用例。

  2. **空串兜底把「跳过」变成「报错」**。
     `test_llm_metering_concurrency.py` 用 `os.getenv(..., "")` 的空串兜底，
     空串过不了 `Settings` 的必填校验 → 抛 `ValidationError` →
     测试变成 **ERROR**（收集期错误）而非 **SKIPPED**，
     把「未配置测试库」这个真实原因掩盖成了「测试代码有 bug」。
     仓库其它 8 个集成测试文件用的是 `getenv` 无默认值 + 显式 `pytest.skip`，
     口径本来是统一的——只有这一个文件漏了。

  3. **探活探测没有连接超时**。
     为「连不上就跳过」加探活时，psycopg 默认会一直等操作系统的 TCP 连接超时
     （本机实测约 **140 秒**）——整个测试会话被这一件事拖住，
     表现为「测试卡住不动」，极易被误判为死锁。

- **修复要点**：

  1. **新增 `tests/integration/conftest.py`** 作为集成测试连接串的**统一入口**：
     按「进程环境变量 → 项目 `.env` 的 `DATABASE_URL` → 内置默认值」三级解析，
     在**导入期**注入 `ANALYSIS_TEST_DATABASE_URL` / `ANOMALY_TEST_DATABASE_URL`。
     第 2 级是**主动解析 `.env` 文件**，绕开「pydantic-settings 不写回 `os.environ`」这个缺口。
  2. **探活加 `connect_timeout=2`**：连不上就在 2 秒内判定为「不可达」，
     **不设**环境变量 → 测试按既有约定**跳过**而不是报连接错误。
     实测从 150 秒降到 **2.57 秒**。
  3. **统一各文件的 skip 口径**：空串兜底全部改为
     「依赖 `db_env` fixture 先触发 skip」或「无默认值 + 显式 skip」，
     保证**任何情况下都不会退化成 ERROR**。

- **修复效果**：

  | 项 | 修复前 | 修复后 |
  |---|---|---|
  | 集成测试 | 9 passed / 71 skipped / **2 errors** | **82 passed / 0 skipped / 0 errors** |
  | 全量测试 | 870 passed / 71 skipped / 2 errors | **943 passed / 0 skipped / 0 errors** |
  | 数据库不可达时 | 约 150 秒（干等 TCP 超时） | **2.57 秒**（跳过，零错误） |

- **回归保障**：`tests/integration/conftest.py` 本身即兜底实现——
  它的三条优先级路径（环境变量 / `.env` / 默认值）各自对应真实场景，
  且「不可达 → 跳过」这条路径经**实测**（指向 59999 空端口）验证过：
  9 passed / 73 skipped / **0 errors**。

> **教训**：**「跳过」和「通过」都是绿色的**——
> 71 个 skip 在 CI 输出里几乎看不出来，
> 只有把 `pytest -q` 的统计行看仔细才会发现。
> 判据：**测试数量突然变少时，先确认是「跳过」还是「真跑」**。
> 更深一层：**「配置读不到」和「配置读到了但没生效」是两回事**——
> pydantic-settings 读 `.env` 与 `os.getenv()` 读环境变量，
> 是两条**互不相通**的路径。

### L-29 `LLM_AGENT_MAX_TOKENS` 声明了却零消费 ⏸ 已列入白名单（2026-11-27）

> **发现于**：开发计划盘点阶段的**机制缺口盘点**。
> 这不是某个具体缺陷，而是**一类缺陷的成因**。

- **问题本质**：本项目累计出现 **11 次**「声明了但没人消费」
  （L-03 / L-07a / L-16 / L-18 / L-19 / L-20 / L-21 / L-23 / L-26 / L-29
  及 `apscheduler` / `langgraph` 两个依赖）。
  每次都能靠**人工 grep** 发现，
  但**每次都得重新记起要查**——
  说明**缺的是机制，不是纪律**。

  更糟的是：这类问题**不会让任何测试失败**。
  L-26 的教训已经写得很清楚——
  「**让 CI 去查，而不是让人记得查**」。

- **修复内容**：

  1. **新增 `src/aicrypto/config/dependency_audit.py`**：
     - `audit_dependencies()`——对账 `pyproject.toml` 的运行时依赖
       与代码里的实际消费证据（**AST 分析**，非正则）；
     - `audit_settings_fields()`——对账 `Settings` 每个字段与消费方；
     - `check_dependency_usage()` / `check_settings_usage()`——
       返回不一致项的描述列表；
     - `check_whitelist_reasons()`——白名单自身合规性
       （**每条必须有非空原因**，否则等于永久豁免）。
  2. **新增 `tests/unit/test_dependency_usage.py`**（29 项），
     并在 `.github/workflows/ci.yml` 加一步
     `Dependency & settings usage check` 作为**常规检查**。
  3. **删除 5 个零消费且无计划的依赖**：
     `python-multipart` / `tenacity` / `tomli-w` / `asyncpg` / `greenlet`
     （后两个来自 `postgres` extra——后端实际用**同步** `psycopg3`，
     异步栈从未落地）。CI 也随之不再安装 `postgres` extra。

- **实现上的三个关键点**（都是踩过坑才定下来的）：

  1. **必须做 AST，不能用正则**。
     正则分不清「注释/字符串里的 `import`」和「真的 import」，
     也分不清 `cfg.FIELD` 和 `ErrorCode.FIELD`。
  2. **必须做类型感知的追踪**：
     - 别名变量（`cfg = get_settings()`）——
       本项目大量把 `Settings` 别名成 `cfg`，只按变量名 `settings` 匹配会漏掉一大半；
     - `@property` 访问器（`cfg.allowed_ips` → `self.ALLOWED_IPS`）；
     - 实例持有的 Settings（`self._settings.MARKET_FUNDING_POLL_SECONDS`）——
       **恰恰是核心配置**（轮询间隔、深度档位、重连上限）。
  3. **必须排除 `settings.py` 自身的引用**——
     那只是同一个配置项在自我校验，改配置仍然不会改变任何行为。
     同样要排除**别的类**的同名常量（如 `ErrorCode.NOTIFY_QUIET_HOURS`）。

- **回归保障（反向验证）**：
  `scripts/verify_test_effectiveness.py` 对 **20 个用例**
  逐个施加「语义等价于目标缺陷」的补丁，确认每个用例**确实会失败**，
  再恢复实现。

  **这一步不是形式**：验证过程中真的抓出了 **3 个问题**——
  1 个**合成夹具缩进畸形**导致 AST 解析失败，
     测试因此「因为错误的原因通过」（看起来绿，其实什么都没验证）；
  2 个**断言方向错误**，只做正向断言，
     实现完全退化也能通过（vacuous pass）。
  这两个问题**如果不靠反向验证，永远不会被发现**——
  它们恰恰是「测试看起来在测东西、实际没测」的两张面孔。

  因此夹具里加了**语法自检**（合成文件必须能被 `ast.parse`），
  断言也改成了**双向**（正向 + 反向探针）。

> **教训**：**「有测试」不等于「测试有效」**。
> 与 L-26 同源但更深一层：L-26 是「清单会失效」，
> 本条是「**验证会失效**」——
> 一个永远绿的测试比没有测试更危险，因为它提供**虚假的信心**。
> 反向验证是唯一能区分「测试有效」与「测试看起来有效」的手段。

### L-31 成本数据有表有写入，但长期没有任何东西读它 ✅ 已修复（2026-11-27）

> **发现于**：第 1 步（成本报表 + 多 Agent）开工前的盘点。
> 与 L-30 同族，但更隐蔽——**这次连「声明」都做对了，只是缺了「读方」**。

- **问题本质**：`llm_cost_records` / `model_runs` 两张表
  有完整的写入方（`services/analysis_worker.py::record_model_run`）、
  有真实数据、有一整套成本口径实现（`services/llm_cost.py`），
  **却没有任何代码读取它们做聚合**。
  项目里**从未存在过任何成本报表**。

  这比 L-30 更难发现：L-30 是「配了没用」，
  本条是「**配了、用了、记了，就是没人看**」——
  从表结构、写入路径、测试覆盖率看，**一切都是绿的**。

  **代价**：所有关于「优化是否值得」的判断都只能靠**文档里的估算**。
  而 `docs/LLM_COST_AND_OPTIMIZATION.md` 里的成本数字
  **全部来自假设**（如「异动触发 17.5 次/天」是未实测假设值，
  文档自己标注了可能 3–5 倍偏差）。
  也就是说：**最需要真实数据的决策，恰恰只能拿到假设数据**。

- **修复内容**：
  1. **新增 `src/aicrypto/services/cost_report.py`**：
     取数（`fetch_cost_rows`）与聚合（`build_cost_report`）分离，
     聚合是**纯函数**；分组维度覆盖
     模型 / 档位 / Agent / Prompt 版本 / 调用状态 / 按日。
  2. **新增 `scripts/report_llm_costs.py`**：只读 CLI，
     支持 `--days` / `--since` / `--until` / `--json`。
  3. **新增 `tests/unit/test_cost_report.py`（29 项）
     + `tests/integration/test_cost_report.py`（8 项，真库）**。

- **核心纪律：未定价 ≠ 免费**（本条的重点）：

  `llm_cost_records.estimated_cost_usd` 是 **NOT NULL**，
  单价缺失时只能写 0（`record_model_run` 里显式标注
  `price_snapshot.priced = false`）。
  因此**直接 `SUM(estimated_cost_usd)` 会把「没登记单价」读成「不花钱」**——
  成本被**系统性低估**，而且**低得没有任何提示**。

  这与 L-05「键缺失 ≠ 费率为 0」是**同一条原则**，
  只是这次发生在**金额**上而不是费率上。

  处置：
  - 费用**只**累加 `priced == true` 的行；
  - 未定价行**单独计数**，且其 **token 仍计入总量**
    （资源消耗是事实，单价缺失只影响「花了多少钱」的答案）；
  - 存在未定价调用时，报表**显式声明「总额是下界」**，
    并列出**哪些模型没价格**——让处置动作（补 `model_pricing`）可执行。

- **实现上的三个决定**：

  1. **取数与聚积分开**：聚合是纯函数，
     因此「未定价 ≠ 免费」这条纪律能在**不碰数据库**的情况下被完整测试。
  2. **`prompt_version` / `status` 从 `model_runs` **LEFT JOIN** 取**
     （`llm_cost_records` 没有这两列，PRD 30.4）。
     用 **LEFT JOIN 而非 INNER JOIN**：
     孤儿成本行被 INNER JOIN 抹掉会让费用**凭空减少**，
     而读者**看不出少了东西**——
     报表**少算**比**多算**更危险。
  3. **本地模型也要登记单价**（0 价即可）。
     否则本地模型的调用永远算「未定价」，
     报表就会一直提示下界——久而久之没人再看那个警告，
     纪律就白设了。

- **回归保障（反向验证）**：
  本条的 15 个反向验证用例已并入
  `scripts/verify_test_effectiveness.py`（现共 35 个用例）。
  **验证当场抓出 1 个 vacuous pass**：
  `test_render_lists_unpriced_models` 原先只断言「全文包含模型名」，
  而模型名同时也会出现在「按模型」分组表里——
  即使警告段完全没提它，断言**也会成立**。
  已改为**只取警告段**来断言。

  > 这与 L-30 抓到的那 3 个问题**完全同源**：
  > **「有断言」不等于「断言有效」**。
  > 连续两次在同一个工具上抓到 vacuous pass，
  > 说明这类缺陷**不是偶发**，而是**默认存在**——
  > 因此反向验证必须是**常规流程**，不是可选动作。

- **顺带澄清**：`model_runs` 表**没有 `tier` 列**——
  按档位分组是成本报表的需求，档位落在 `llm_cost_records.tier`。
  这与 `docs/LLM_COST_AND_OPTIMIZATION.md` §6.2 的说明一致。
