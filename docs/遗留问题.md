## 一、阻断级（会导致数据错误或功能不可用）

### L-01 SPOT 市场会误拉衍生品数据 ✅ 已修复（2026-11-24）

> **修复摘要**：新增 `MARKET_CAPABILITIES` 能力表 + `supports()` 判定函数；
> client 层加 `_get_supported()` 守卫（发请求前拦截，抛
> `UnsupportedMarketError`）；collector 按能力**不排期**衍生品轮询，
> 且现货不订阅 `markPrice` 流；`_guard` 单独捕获
> `UnsupportedMarketError`，不再累加 `_rest_failures`。
> 回归测试见 `tests/unit/test_market_capabilities.py`（16 项）。

- **原始现象**：`derivatives_collector.py` 对每个 `market_type` 都执行全套轮询，包括
  持仓量、资金费率、OI 历史。但这些是**衍生品专属**数据，现货市场没有。
  `binance_derivatives.py` 里 `OI_PATH` / `FUNDING_RATE_PATH` /
  `PREMIUM_INDEX_PATH` / `OI_HISTORY_PATH` **全部是 `/fapi/` 路径**，
  与 `BASE_URLS["SPOT"]`（`api.binance.com`）拼接后会形成无效 URL。
- **影响**：
  - 现货 collector 持续发起注定失败的请求。实测 `api.binance.com/fapi/v1/openInterest`
    与 `/fapi/v1/fundingRate` 均返回 **403**（不是超时），请求会立刻失败，
    但每次都要消耗限流配额；
  - **会污染质量事件表**：403 走 `raise_for_status()` 抛 `httpx.HTTPStatusError`
    → 被 `_guard` 捕获并累加 `_rest_failures` → 连续 3 次后触发
    `_record_stale()`，往 `market_data_quality_events` 写入
    **CRITICAL / STALE** 事件。这些事件**不是真实的数据质量问题**，
    而是「现货市场本来就没有衍生品数据」导致的必然失败；
  - 现货的 `markPrice@1s` 流不存在（该流仅 USDⓈ-M 有），WS 订阅无意义。
- **数据不会串**（已实测确认）：`parse_open_interest` 等解析函数的 `market_type`
  是**显式传入**的，即使端点返回了可用响应，落库时也会正确标记为 `SPOT`，
  不会把期货数据标成现货。真正的问题是**虚假的质量告警**而非数据污染。
- **当前缓解**：`config/base.toml` 的 `market_types` 含 `SPOT`，
  但 `.env` 通常只跑 `--market-types USDM_FUTURES`（脚本默认读 `MARKET_TYPES`，
  **默认包含 SPOT**）。
- **建议修复**：在 `DerivativesCollector` 中按 `market_type` 分流——
  - `USDM_FUTURES`：全量（OI / funding / markPrice / 盘口 / 成交）；
  - `SPOT`：仅盘口深度 + 聚合成交（基差计算需要现货报价，见 29.6）。
  端点路径也需按市场选择，不能只按 base URL 切换。
- **PRD 依据**：29.2.1（订阅清单按 `symbol × market_type` 区分）、
  29.6（基差需现货与期货双侧）。
- **修复后的行为**（已用 mock transport 实测）：
  - 现货 collector 只发出**盘口深度**请求，OI / funding / premiumIndex
    在 HTTP 层之前就被拦截，请求数从 4 降到 1；
  - 现货的 WS URL 不含 `markPrice`，期货仍包含；
  - `UnsupportedMarketError` 走 `_guard` 的独立分支，不产生质量事件。

### L-02 资金费率陈旧阈值定义但从未使用 ✅ 已验证

- **现象**：`derivatives_collector.py` 定义了
  `FUNDING_STALE_THRESHOLD_SECONDS = 120.0`（29.4.3：资金费率当前值允许滞后 2 分钟）
  与 `FUNDING_HISTORY_STALE_THRESHOLD_SECONDS = 8 * 3600.0`（历史允许 1 个周期），
  但**两个常量都没有任何调用点**。全仓 grep 仅命中定义处与 `__all__`。
- **影响**：资金费率数据陈旧时**不会**产生 `DATA_STALE` 质量事件。
  只有 OI 走通了 `_check_oi_staleness`。
  下游按 29.4.3 判定「资金费率是否可信」时缺少依据；
  PRD 29.4.3 的表格明确要求 `funding_rate` 当前值超 2 分钟即判 `DATA_STALE`。
- **建议修复**：在 `_poll_funding` 后补陈旧判定，参照 `_check_oi_staleness`：
  - 当前值（WS `markPrice`）比对最近一次推送时间，阈值 120s；
  - 历史记录比对 `funding_time` 与拉取时间，阈值 8h。
  两者都需写 `market_data_quality_events` 并更新指标。

### L-03 数据保留与清理完全未实现 ✅ 已验证

- **现象**：
  - `MARKET_TRADE_RETENTION_DAYS`（默认 90）已在 `Settings` / `catalog.toml` /
    `.env.example` / PRD 32.4 声明，但**没有任何代码读取它**；
  - `RETENTION_ENABLED` 同样只定义未使用；
  - `market_trades` / `orderbook_snapshots` 没有任何清理任务。
- **影响**：PRD 27.3 估算聚合成交约 5–15 MB/日、盘口快照按每分钟 1 次持续增长。
  长期运行会**无上限膨胀**，直接违反 27.3「原始高频数据短期保留 + 派生特征长期保留」
  与 27.4「明确每类数据的保留期与清理任务（`scheduled_jobs` 中的 `retention` 任务）」。
  PRD 37.7 的容量预期也基于「90 天后清理」这一假设。
- **建议修复**：
  1. 实现 `retention` 清理服务（按 `MARKET_TRADE_RETENTION_DAYS` 清理
     `market_trades`，盘口快照设更短保留期）；
  2. 与 P5 调度层合并实现（PRD 27.4 明确要求放在 `scheduled_jobs` 的 `retention` 任务里）；
  3. 清理前先把聚合特征（如分钟级 taker 流量）落库，避免丢掉可复用的派生数据
     （27.3 原文「90 天之后只留聚合特征」）。

## 二、正确性风险

### L-04 盘口快照无保留策略 ✅ 已验证

- **现象**：`orderbook_snapshots` 每分钟 1 条、每条含 top20 双向 JSONB，
  **没有任何保留期配置或清理逻辑**。PRD 27.3 只写了「原始深度不长期保留」，
  未给出具体天数，而 `Settings` 里也没有对应配置项。
- **影响**：这是四张衍生品表里**增长最快**的一张。按 2 币种 × 2 市场 × 1440 条/日
  × 每条约 2–4 KB 估算，约 8–23 MB/日，一年可达 3–8 GB。
- **建议修复**：新增 `MARKET_BOOK_RETENTION_DAYS`（建议 7–30 天），
  与 L-03 一并落地清理任务。

### L-05 `funding_history` 权威口径与 WS 预估费率未打通 ✅ 已验证

- **现象**：`markPrice@1s` 流携带**当前预估资金费率**，
  PRD 29.2 明确它是 `DER_FUNDING_EXTREME` 的低延迟触发源，
  且「`funding_history` 表仍以 REST 为权威」。
  当前实现把 WS 费率只写进 `self._mark_prices` 内存字典与 Prometheus 指标，
  **没有写入任何表**，也没有供异动规则消费。
- **影响**：`DER_FUNDING_EXTREME` 无法做到低延迟触发——只能等 REST 轮询
  （默认 600s）才能看到最新费率。`self._mark_prices` 是个**只写不读**的字典，
  属于死代码。
- **建议修复**：P3 接入 `DER_FUNDING_EXTREME` 时，把 WS 费率作为触发源接入
  异动引擎（写 `anomaly_events`，但**不回写** `funding_history`，
  因为那会违反「已结算事实不可改写」的幂等约定）。

### L-06 多空偏向与价格/OI 背离永远无法产出 ✅ 已验证

- **现象**：`domain/market/derivatives.py` 的 `long_short_skew()` 接收
  `price_change_pct` 参数，但 `derivatives_snapshot.py` 调用时**恒传 `None`**：
  ```python
  "long_short_skew": long_short_skew(
      oi_change=oi_change,
      funding_rate=funding_rate,
      price_change_pct=None,   # <- 恒为 None
  ),
  ```
- **更严重**：领域层已实现 `price_oi_divergence(price_change_pct, oi_change)`，
  但**全仓没有任何调用点**（只在其定义处与 `__all__` 出现）。
  快照里的 `price_oi_divergence.detected` 是**手写的字面量 `False`**，
  不是计算结果。
- **影响**：多空偏向与价格/OI 背离这两项衍生品信号**永远无法真正产出**。
  PRD 22.2.4 的 `DER_LS_SKEW` 与 `DER_PRICE_OI_DIVERGENCE` 都依赖这个值。
  注意 `long_short_skew` 传 `None` 时返回 `NEUTRAL`——**不会报错**，
  属于静默失效：快照看起来正常，但信号恒为中性。
- **建议修复**：从 `market_candles` 取对应周期（如 1h）的价格变化率传入，
  并改用领域层的 `price_oi_divergence()` 替代手写字面量。
  `analysis_worker` 里已有 candles 上下文，接入成本低。
  需在 PRD 22.2.4 核对「背离」的精确定义（OI 涨 + 价格跌 等组合）。

### L-07 衍生品特征未参与异动扫描 ✅ 已验证

- **现象**：`anomaly_scan.py` 的规则引擎只覆盖价格 / 成交量 / 波动率类规则。
  `config/base.toml` 的 `[anomaly.rules.derivatives]` 已配好阈值
  （`oi_change_warn_pct = 3.0`、`funding_abs_warn = 0.0005` 等），
  但**没有任何代码读取该段配置**（全仓 grep `oi_change_warn_pct` 无命中）。
- **影响**：P2 的数据采集了但**没有消费者**，衍生品异动规则全部未启用。
  这是 P3 的核心工作项。
- **建议修复**：P3 实现 `DER_*` 规则族，并从 `config/base.toml`
  读取阈值（注意：修改任一阈值必须递增 `rule_version`，见 base.toml 注释）。

### L-14 Docker 服务必须用 `127.0.0.1` 而非 `localhost` 连接 ✅ 已验证

- **现象**：集成测试「挂起」不结束——`create_engine()` 卡在 `connect`，
  单个测试耗时 131 秒才通过（此前全量仅需 13 秒）。
  逐步二分定位到 TCP 层：
  - `127.0.0.1:5432` → 连接耗时 **0.01s**（正常）；
  - `localhost:5432` → 连接耗时 **8~20s**（每次都触发 `connect_timeout`）。
- **根因**：Windows 的 `localhost` 同时解析出 **IPv6 `::1`**（AAAA 记录，优先）
  与 IPv4 `127.0.0.1`。Docker Desktop 发布的端口**只监听 IPv4**，
  因此 IPv6 连接会挂起直到超时，再回退到 IPv4——
  表现就是「每次连接都慢一个超时周期」，而不是直接报错。
  操作系统 hosts 文件里 `::1 localhost` 已被注释，
  解析结果由 DNS 提供。
- **影响**：
  - 本地跑集成测试时，**每个数据库连接**都会白等一个超时周期，
    17 个集成测试累积起来就是十几分钟，且**不报错**、只是极慢，
    极易被误判为「测试死锁」或「代码性能问题」；
  - 真实配置**已经是正确的**：`.env` 与 CI 都用 `127.0.0.1`，
    因此**不影响 CI，也不影响正常开发流程**；
  - 但任何临时用 `localhost` 拼连接串的命令或脚本都会踩坑。
- **建议**：
  - 本地临时起服务时，连接串统一写 `127.0.0.1`（`.env.example` 已如此）；
  - 若使用 `localhost`，需确保 Docker 侧也发布 IPv6，或在 hosts 中
    显式把 `localhost` 指向 `127.0.0.1`；
  - **排查提示**：连接慢但最终成功 → 先比对 `127.0.0.1` 与 `localhost`
    的耗时差异，而不是怀疑数据库负载或代码死锁。
